# SME24

AI powered EHS consulting marketplace for regulated companies in Switzerland. One Next.js app serves the marketing site and three signed in areas (client `/app`, expert `/expert`, ops `/admin`). Product plan: `docs/scope/index.md`. Every stack decision and its reason: `docs/specs/0001-stack-architecture/index.md`.

## Stack

- **Language / Runtime**: TypeScript, strict mode plus `noUncheckedIndexedAccess`, everywhere (app, tasks, scripts); Node 22 (`.nvmrc`, `engines`)
- **Framework**: Next.js 16 App Router with React 19 Server Components; Node runtime only (no Edge), Vercel functions in `fra1`
- **Key dependencies**: Supabase in Zurich (Postgres, Auth, Storage, Realtime) through `@supabase/ssr` with RLS always on and no ORM; Trigger.dev v4 (EU) for all long running work; Tailwind v4 with shadcn/ui; next-intl v4 (`en` default, `de`); Zod v4; Sentry EU and PostHog EU; Resend with React Email for product email (Mailpit over SMTP locally); Vercel AI SDK v7 through the AI Gateway (`anthropic/claude-sonnet-5`) for every model call; Parallel Task API for company research (a fixture provider locally); Stripe (Node SDK, a restricted key) with `swissqrbill` for package checkout and QR-bill invoices.
- **Package manager**: pnpm

## Build approach

Tracer Bullet (vertical slices; each feature runs end to end through database, background jobs, API and UI, real and deployable, narrow rather than mocked). Workflow tier: GA (`/develop`, then `/check verify`, `/test`, fresh model `/check review`, `/document`).

## Commands

```bash
pnpm install                 # Node 22 via .nvmrc; Docker and the Supabase CLI are needed too
supabase start               # local Postgres, Auth, Storage, Realtime; applies migrations and seed.sql; Mailpit inbox at http://127.0.0.1:54324
pnpm dev                     # http://localhost:3000 redirects to /en (falls to 3001 when 3000 is busy)
pnpm build                   # next build
pnpm budget                  # first load JavaScript of the prerendered pages against the per page budget; exits 1 when a page is over, when the browser Sentry SDK sits in a module script, or when zod reaches a content page; `--url <deployment>` measures a deployment with VERCEL_AUTOMATION_BYPASS_SECRET (docs/marketing.md)
pnpm register:build          # rebuild src/features/marketing/register.json from the SGAS export (hand run; drops the address, phone, email and website columns before writing; commit the file)
pnpm typecheck               # next typegen + tsc --noEmit
pnpm lint / pnpm lint:fix    # Biome: lint, format, import order, a11y rules
pnpm test                    # Vitest + Testing Library (tests/, src/**/*.test.*)
pnpm test:e2e                # Playwright + axe (e2e/); starts its own dev server on port 3100, reads .env.local, 2 workers locally; the email flows go through Mailpit, so they run on the local stack only and skip on a deployment; the welcome email and research specs assert on a task only with `TRIGGER_DEV_RUNNING=1` while `pnpm trigger:dev` runs
pnpm test:db                 # pgTAP policy tests in supabase/tests/; needs the local stack running
pnpm db:diff <name>          # migration from supabase/schemas/ (declarative sync)
pnpm db:reset && pnpm db:types   # reapply locally, then regenerate src/lib/supabase/database.types.ts (CI fails when stale); never from a second worktree, they share one local stack and a reset silently skips the other's migrations
pnpm trigger:dev             # Trigger.dev tasks locally (needs a project ref; the `trigger` binary comes from the pinned `trigger.dev` dev dependency)
pnpm email:dev               # React Email preview server on port 3200, one preview per template and language (src/lib/email/previews/)
pnpm user:invite --email <address> --role expert|ops [--locale de|en] [--name "…"]   # invite a staff user with the role fixed; needs the target environment's Supabase keys in .env.local (docs/auth.md)
pnpm users:seed [--dry-run]  # the hosted counterpart of supabase/seed.sql: the four role test accounts, confirmed, with generated passwords printed once; refuses a database holding any other user (docs/auth.md)
pnpm benchmarks:migration    # generate supabase/migrations/<timestamp>_benchmark_seed.sql from supabase/seed-data/*.csv (commit the file; then db:reset and test:db)
pnpm benchmarks:recompute    # trigger benchmark-company for every company with a snapshot; reads the target environment's Supabase and Trigger.dev keys from .env.local (docs/benchmark.md)
pnpm questionnaires:build    # rebuild src/features/assessments/content/{iso45001,compliance}.json from the raw HTML exports in the gitignored docs/raw/ (hand run; drafts the German through the AI Gateway and flags it deReviewed:false; --no-translate refuses to write unless every German is reused; commit the files)
pnpm questionnaires:migration  # render supabase/migrations/<timestamp>_questionnaire_seed.sql from the committed JSON (upserts only, never a delete, so a rerun changes no row count; commit the file)
pnpm directory:import <path-to-xlsx> [--dry-run] [--batch "<name>"]   # hand run load of the purchased contact list from a path outside the repo; refuses a hosted database until IMPORT_POLICY.status is 'cleared', prints counts only and never an address, a name or a company name (docs/directory.md)
```

## Specs

Stored in `docs/specs/`. Format: `docs/specs/NNNN-title/index.md` (decision and build plan) with `rationale.md` beside it.

## Rules

- **Functional style.** Pure functions and plain data; classes only for `Error` subclasses. Side effects (Supabase, Trigger.dev, fetch, cookies) live at the edges: `actions.ts`, `queries.ts`, `src/trigger/`, `src/lib/`. Module level values are constants; never a module level Supabase client.
- **Immutable data.** `const`, `readonly`, spread over in place mutation; `map`/`filter`/`reduce` where they read better than loops.
- **One error handling pattern.** Server actions return a typed result (`{ ok: true, data }` or `{ ok: false, error }`) and never throw for expected failures; queries throw; tasks throw so Trigger.dev retries. Unexpected errors go to Sentry; breadcrumbs use `log` from `src/lib/logger.ts` (structured JSON to stdout).
- **Validate at the boundary.** Every form and server action parses its input with the feature's Zod schema in `schema.ts`; the same schema types the form.
- **Named exports only outside `src/app/`.** Default exports only where Next.js requires them (pages, layouts, route files) and in config files.
- **Document every exported function** with a one line JSDoc: what it does and which context runs it (server component, action, proxy, task, browser).
- **Feature folders.** `src/features/<domain>/{ui/,actions.ts,queries.ts,schema.ts}`; shared infrastructure in `src/lib/`; shadcn primitives in `src/components/ui/`; routes stay thin.
- **Data access through the four client factories** in `src/lib/supabase/`, one per execution context. RLS is the real boundary; the proxy only gates areas and never redirects a server action post (a redirected POST keeps its method and lands on a page whose HTML the router cannot read as an action reply). The service client (bypasses RLS) is allowed only in `src/trigger/` and server only code, enforced by Biome; tasks take explicit ids and filter by them.
- **Database changes** start in `supabase/schemas/*.sql` (table, RLS and policies in the same file), then `pnpm db:diff`, `db:reset`, `test:db`, `db:types`. Migrations stay backward compatible (add, switch, remove later) because previews share staging. The diff misses four things that must be fixed by hand in the migration: column grants dropped by a table level `REVOKE ALL`, the `anon` execute revoke on a new `public` function, a view body rewritten from `select *` to a column list, and a view grant widened from `SELECT` to full DML for `authenticated`. Read every generated migration before committing it; the diff also re-emits unchanged functions, which are harmless but noise. Every new kind T (tenant) table copies the tenant table contract from spec 0002 and gets a pgTAP file in `supabase/tests/`.
- **Membership rows are never inserted directly.** Direct `INSERT` on `organization_members` is revoked for the app roles; an owner adds a member through `public.add_organization_member`, which checks the target consented. Nothing in `src/` calls it yet; feature 22 (client team invitations) does.
- **Auth flows follow `docs/auth.md`** (spec 0005). Every emailed link goes through `/api/auth/confirm` and is verified from its token hash (never `{{ .ConfirmationURL }}` in a template); `profiles.terms_accepted_at` is written only by the profiles trigger or `accept_terms()`; the role never comes from user input (the profiles trigger defaults to `client`, only `pnpm user:invite` sets `expert` or `ops`). Auth email templates live in `supabase/templates/` (German above English) and the hosted settings (Resend SMTP, templates, Google and Microsoft) are a per environment checklist in `docs/auth.md`.
- **Product email and ops alerts follow `docs/email.md`** (spec 0006). Every product email goes through `sendEmail` in `src/lib/email/send.ts`, which triggers the `send-email` task: one `email_deliveries` row per send, a React Email template from the registry rendered in the recipient's stored language, Resend when `RESEND_API_KEY` is set, else SMTP through `EMAIL_SMTP_URL` (Mailpit locally), else `skipped`; never call a transport directly. Team alerts go through `sendOpsAlert` in `src/lib/alerts/` and the `ops-alert` task to the Slack webhook. A new template is a schema entry, a component, a registry entry, `email.<name>` keys in both catalogs and a preview; a new alert kind is a schema plus a presenter. Auth emails stay on the Supabase path in `docs/auth.md`. Ops watch deliveries on `/admin/emails`; the per environment checklist (domain, keys, webhook, allowlist, Slack) lives in the runbook.
- **Company research follows `docs/research.md`** (spec 0007). `requestResearch` in `src/features/research/actions.ts` inserts the company and a `queued` run and triggers the `research-company` task under the idempotency key `research/<runId>`; the database holds the guards (one open run per company, five runs per organization per rolling 24 hours), never the app. Providers implement the interface in `src/lib/research/provider.ts` (Parallel and the fixture are interchangeable; a second provider is a file in that folder); `RESEARCH_PROVIDER` is `fixture` whenever `PARALLEL_API_KEY` is empty and a deployed task without the key refuses to start. Every model call goes through `structuredOutput` in `src/lib/ai/gateway.ts` (AI SDK v7 through the AI Gateway, prompts versioned in `src/lib/ai/prompts/`); nothing else imports `ai`. A new KPI is a `kpi_definitions` seed row plus a catalogue entry in `src/features/research/catalogue.ts` (a Vitest test keeps them equal); a new error code is a `research_runs.error_code` value plus `research.errors.<code>` keys in both catalogs. The per environment checklist (Parallel key, gateway key, schedule, Slack, spike, firewall) lives in the runbook.
- **Peer benchmark follows `docs/benchmark.md`** (spec 0008). The `benchmark-company` task runs after a research run ends `succeeded` (key `benchmark/run/<runId>`), after `updateCompanyFacts` in `src/features/benchmark/actions.ts` (key `benchmark/edit/<companyId>/<updated_at>`) and on `pnpm benchmarks:recompute`; it hands stored rows to the pure `computeBenchmark` in `src/features/benchmark/model.ts` and inserts one immutable `benchmark_snapshots` row (written only by the service role), which the dashboard reads through the version keyed `SNAPSHOT_SCHEMAS` in `snapshot.ts`; no model call anywhere. A formula change bumps `MODEL_VERSION` in `src/features/benchmark/catalogue.ts` and adds a schema to the map, never rewrites old rows. Peer values and the seven assumptions live in `supabase/seed-data/*.csv` and reach the database only through `pnpm benchmarks:migration`; every first seed row is `provisional`, and the launch gate in the runbook requires zero provisional rows in production (spec 0016 split that flag from `is_assumption`, so the gate is two queries).
- **Client entered KPIs follow `docs/benchmark.md`** (spec 0010). The "Your figures" card in `src/features/self-assessment/` writes the same `company_kpis` table as research with `source 'client'`: `saveClientKpis` reads then writes (the client unique index is partial, so PostgREST cannot upsert onto it) and `clearClientKpi` deletes one row so the research value shows again; both queue `benchmark-company` with `triggerKind 'client_edit'` under `benchmark/kpis/<companyId>/<moment>` and `benchmark/kpis-clear/<rowId>`, and both answer a typed result, never throw. Every hand entered value belongs to one reporting year from the pure rules in `years.ts` (`currentYear` reads the server clock in `Europe/Zurich`); the form parses with the `clientKpisFormSchema(currentYear)` factory and sends only the fields the client changed, so an untouched research value is never copied into a client row. Strings live in the `selfAssessment` namespace in both catalogs. The update and delete policies are per creator until feature 22 relaxes them to organization scope.
- **Derived injury counts follow `docs/benchmark.md`** (spec 0012). The expected yearly lost time and recordable injury counts are a display only `derived` block of the benchmark snapshot, never a KPI: `kpi_definitions` gains no row, `company_kpis` gains no source, and the counts never appear in `inputs.kpis`, `results` or `gaps`. `exposureCount(shape, rate, fte, hoursPerFte)` in `src/features/benchmark/model.ts` is the one place a rate becomes a count, dispatching on the rate's shape (`per_1000_fte` or `per_million_hours`) rather than on `costAt`'s incident union; `costAt` delegates only its `incidents` line, and the two may name different input rates on purpose (`rationale.md`). The whole block is `null` without a positive `inputs.fte` or without the `hours_per_fte` assumption row, and no derived value ever carries a confidence. `SNAPSHOT_SCHEMAS` in `snapshot.ts` is keyed by literal versions (`"benchmark-model@1"`, `"benchmark-model@2"`, `"benchmark-model@3"`, `"benchmark-model@4"`), so a `MODEL_VERSION` bump adds a key and never renames the only one; the `benchmark-company` task looks its write schema up by version rather than naming a schema, or zod strips the new block before the insert. A deploy owes `pnpm benchmarks:recompute`, watched: a stored row keeps the version it was written under until it is recomputed, and a recompute moves every block, not just the derived one. The script keys each trigger on `benchmark/recompute/<companyId>/<UTC day>` with a 24 hour TTL, so a second run on the same UTC day hands back the earlier runs and writes no new row; a post deploy recompute needs a UTC day no earlier recompute used.
- **Peer honesty follows `docs/benchmark.md`** (spec 0016). Two flags, never both true: `provisional` means a value has not yet been read from its named source, `is_assumption` means no published source exists for it, so the launch gate is two queries and only the three `indirect_multiplier*` rows may answer the second. A peer row's shape is derived from its values in `seed-migration.ts` (`p25 == median == p75` is a `point` row), never a CSV column and never hand typed; a point row gets `above_average` or `below_average` from `positionOf` (the `iso_45001_certified` branch routes through the same rule), renders text only with no `QuartileBand` and no replacement graphic, and the words quarter, quartile and median never appear on it in either language, which `tests/features/benchmark/catalogue.test.ts` enforces over both catalogs. The CHF headline is a range on the card and in the `benchmark_ready` email alike, both rounded outward by `roundChfRange` in `model.ts` so the displayed band always contains the computed one and the two surfaces can never disagree for one snapshot. A curator's caveats reach the client rather than dying in the database: `source_key` and `basis` on a peer row, `note` and `isAssumption` on an assumption. Every KPI declares a `peerStatus` and a `peerNote` in `src/features/research/catalogue.ts`, so a sourceless KPI says so instead of looking pending. `docs/benchmark.md` records the confirmed dead ends; do not re investigate them.
- **The marketing site and enquiries follow `docs/marketing.md`** (spec 0009). The public pages under `src/app/[locale]/(marketing)/` stay static (seven marketing plus the four legal ones from spec 0015): nothing on that path reads `searchParams`, `headers()` or `cookies()`, the routes and their German slugs live in `PATHNAMES` and `MARKETING_ROUTES` (`src/i18n/pathnames.ts`), and every page carries `marketingMetadata`, an `opengraph-image.tsx` beside it and a `JsonLd` block. Copy is `marketing.*` keys in both catalogs; a price is `PACKAGES` in `src/features/marketing/packages.ts` and a contact fact is `SITE` in `site.ts` (a placeholder goes on `SITE_PLACEHOLDERS`, which a test keeps empty). Both buyers are in play (the safety manager and the CFO), and since the client review of 2026-09-11 (spec 0009, fifth amendment) the headline leads with the benchmark, "Benchmark your risks. Find your savings. Fix it – once.", and the franc figure is the proof beneath it, on the marketing pages and in their metadata alike. The dashboard heading and the email subject already lead with the benchmark, so the later pass they were held for is closed with no change. The expert register at `/expert-network/directory` is a static build artifact: `scripts/build-register.mts` behind `pnpm register:build` maps the SGAS export to `register.json`, dropping the address, phone, email and website columns in the script so they never enter the repo, and `register.ts` holds the pure filter and count functions the page and its tests share. A page that renders a grouped four digit number in a client component defers it until mount, because ICU groups it differently on Node and in the browser and the hydration mismatch leaves every control on that component inert. `submitEnquiry` in `src/features/marketing/actions.ts` runs the honeypot, the mount timing check and two counted rate limits, stores the address as a SHA 256 hash and then, never losing the row, fires the `enquiry.received` alert, the `enquiry_received` acknowledgement and the `enquiry_sent` event; ops work the rows in `src/features/enquiries/` and `purge-enquiries` handles retention. Browser code reads public variables through `@/lib/env.public` (zod must not reach the browser) and Sentry loads after the page in `src/instrumentation-client.ts`, both enforced by the Biome override; `pnpm build && pnpm budget` is the gate. The per environment checklist (owner facts, `NEXT_PUBLIC_APP_URL`, the schedule, the webhook, Rich Results, Lighthouse, production robots) lives in the runbook.
- **Package checkout and Swiss VAT follow spec 0011** (`docs/specs/0011-package-checkout-swiss-vat/index.md`). Every amount is whole Rappen in `bigint` columns, computed only by the pure `computeAmounts` in `src/features/checkout/money.ts`; no float ever carries money and `gross_rappen = net_rappen + vat_rappen` is a check constraint, not app code. Payment confirmation reaches the database only through `/api/webhooks/stripe`, never the browser, and `settleOrder` in `settle.ts` is the single resumable core that writes `paid`, draws the gapless invoice number and enqueues the follow up work. App roles have `UPDATE` on `orders` revoked, so `startCheckout` stores the Stripe session id through the lazy `Actor.service()` client that `requireClient` mints after authorization (the same shape as `requireOps`), and it withholds the payable URL unless that write is confirmed, because the sweep reads a null session id as an order nobody can pay. Any URL handed to Stripe or a buyer interpolates `LOCALE_CODE[locale]` (the short `de` and `en`), never the locale object. A Trigger.dev task that must act once after retries are exhausted uses `onFailure`, never `catchError`, which runs on every attempt.
- **Expert accounts and profiles follow `docs/experts.md`** (spec 0013). Ops invite from `/admin/experts/new` through `inviteExpert`, which calls the shared `inviteStaffUser` in `src/lib/auth/invite.ts` — the same module `pnpm user:invite` runs, so the page and the script create the same rows in the same order and the role is a literal in the action, never a form field. The `expert_profiles` row is created at invite time with the email copied onto it, so the ops list is one query. `set_expert_status` is the only write path for the status and `set_expert_photo` the only one for `photo_path`, so both columns sit outside the profile action's column grant; assignment eligibility is the `check_expert_assignable` trigger in the database, never the app, so a deactivation racing an assign can never land on an inactive expert. Photos live in the private `expert-photos` bucket at `<expert_id>/photo.<ext>` and every read is a ten minute signed URL through `photoUrl` on the caller's user client, never a public URL and never the service client. Every list field is a code from `EXPERT_CATALOGUE` in `src/features/experts/catalogue.ts` with both labels, kept equal to the check constraints by a Vitest test, so adding a standard is a migration; strings live in the `experts` namespace in both catalogs. `deactivateExpert` is idempotent on purpose (status, then the open assignments, then the ban), so a failure part way through is fixed by pressing the button again. The three emails and the `expert.onboarded` alert ride the rail in `docs/email.md`; the invite itself stays an auth email on the Supabase path in `docs/auth.md`. The per environment checklist (the bucket, a real invite, the Slack alert, the three emails, `/admin/emails`) lives in `docs/experts.md`.
- **Ops admin, orders and scheduling follow spec 0014** (`docs/specs/0014-ops-admin-orders-scheduling/index.md`). The order is the delivery record: `scheduled_at`, `assigned_expert_id`, `delivered_at` and `scheduled_by` are four nullable columns on `orders`, and the three delivery states (`scheduled`, `in_progress`, `delivered`) ride the same `status` column as the payment states, extended additively. Every edge, the future date check on `paid -> scheduled` only, and the delivery column consistency guard live in the `private.check_order_transition` and `orders_check_delivery_columns` triggers in `supabase/schemas/41_orders.sql`, never in the app; the actions in `src/features/ops-admin/actions.ts` map the refusals through the pure `classifyScheduleError` in `errors.ts`, which matches the fragment each `raise exception` writes. `UPDATE` on `orders` is revoked from every app role, so each action authorises the caller itself and then writes through the service client `requireOps` mints, because the proxy never runs for a server action post. `scheduleOrder` also upserts the active `expert_assignments` row, which is what actually grants the expert access. Strings live in the `admin` namespace in both catalogs, and the `assessment_scheduled` email rides the rail in `docs/email.md`.
- **Legal pages, consent and data requests follow `docs/legal.md`** (spec 0015). No analytics library loads before a choice: the `sme24_consent` cookie (`granted:<version>` or `denied:<version>`, a stale version counting as no answer) is written only by `setConsent` and `clearConsent` in `src/features/legal/actions.ts`, never by browser code assigning `document.cookie`, and the gate in `src/lib/analytics/client.tsx` is the one place that may call `posthog.init`. Withdrawal clears the `ph_` prefixed storage and cookies itself rather than calling `posthog.reset` or `opt_out_capturing`, because both return early while `__loaded` is false, so a withdrawal after a reload would clear nothing. Every fact on the four static pages under `src/app/[locale]/(marketing)/{privacy,terms,imprint,cookies}/` comes from a constant (`PROCESSORS` and `RETENTION` in `processors.ts`, `SITE`, the dates in `dates.ts`), never from prose, and `docs/legal/record-of-processing.md` is the table by table record a pgTAP test keeps honest. `CURRENT_TERMS_VERSION` in `terms.ts` is compared by equality, never by ordering (the column is `text`, so `'10' < '2'`), and bumping it blocks every signed in user behind a dialog, so it also owes a `legal.terms.changelog.<version>` key in both catalogs and a `TERMS_VERSIONS` entry. `data_requests` carries one open row per person per kind through a partial unique index rather than an application read, `UPDATE` is revoked from every app role so `updateDataRequest` authorises the caller and writes through the service client, and fulfilling a deletion runs `anonymisePerson` before recording the fulfilment, deliberately leaving `orders`, `invoices`, `order_events` and `stripe_events` alone for the ten years Art. 958f CO requires. `DATA_REQUEST_TRANSITIONS` in `schema.ts` is the state machine, because there is no database trigger for it. Strings live in the `legal` namespace in both catalogs; the `data_request.received` alert rides the rail in `docs/email.md`. The bar is fixed to the bottom of the viewport from the root layout, so it covers the signed in areas and the public pages alike: anything anchored to the bottom of either must reserve the height it publishes as `--consent-bar-height` (the signed in sidebar footer in `app-sidebar.tsx` and the marketing wrapper in `(marketing)/layout.tsx` both do), or an opaque bar lands on the focused control and nothing there can be clicked. The per environment checklist (the four pages, zero PostHog requests before a choice, the Slack alert, one real export and one real deletion, the lawyer's pass as feature 26's launch gate) lives in `docs/legal.md`.
- **Analytics events and monitoring follow `docs/analytics.md`** (spec 0017). Every event name is a member of `ANALYTICS_EVENTS` in `src/lib/analytics/events.ts` with a Zod schema beside it in `analyticsProperties` (`catalogue.ts`) under an `as const satisfies Record<AnalyticsEvent, z.ZodType>` check, so a name without a schema fails the typecheck and a free string never reaches `captureServerEvent`; names are `object.verb_past` with a dot, matching `ALERT_KINDS`. Every schema requires `locale` (the short `de` or `en` through `LOCALE_CODE`, never the locale object), and an event a signed in person fires also requires `organizationId` while one that can precede an account declares none, so no call site invents a placeholder. Events carry ids and codes only: no email address, no contact name, no company name and no free text, enforced by the schema rather than the call site because `z.object` strips what it does not declare. Capture is fire and forget: a bad payload, an unconfigured PostHog and a transport failure all log and return `false`, never throwing into a server action's typed result or a task's retry, so a dropped event is the deliberate failure mode. Call `captureServerEvent` **after** the write that makes the work durable, and in a task pass a `dedupeKey` keyed on the run id (PostHog's event `uuid`), or a retried attempt that crashed mid run double counts one logical run. The nine server side events need no consent and are captured wherever the server can see them; `benchmark.viewed` is the one browser event and rides the consent gate in `src/lib/analytics/client.tsx`, so it undercounts by the rejection rate and is never compared directly against the server steps around it. A failed task reaches Slack through the `task.failed` alert from `tasks.onFailure` in `src/trigger/instrumentation.ts` (never `catchError`), best effort so it cannot mask the failure that caused it. Sentry tags every event with a release from the Vercel commit SHA, inlined by `next.config.ts` rather than read from `NEXT_PUBLIC_VERCEL_GIT_COMMIT_SHA`. The funnel is a saved PostHog insight per environment, and the per environment checklist (both PostHog keys including Trigger.dev, the Sentry build secrets, the Slack webhook, the funnel, consent, server events surviving rejection) lives in the runbook.
- **The contact directory follows `docs/directory.md`** (spec 0018). The purchased list never enters the repository: no seed, no fixture, no migration and no screenshot carries a real row, and it reaches the database only through the hand run `pnpm directory:import`, which refuses a hosted database until `IMPORT_POLICY.status` in `src/features/directory/import-policy.ts` is `'cleared'` in a commit that also carries the lawyer's dated `licenceNote` and the countries they named (the launch gate, AC-17). The six `directory_*` tables carry no select policy for `authenticated` but the ops one, so the database is the only thing that ever masks or reveals a value: `directory_search` and `directory_unlocked_contacts` are the only read paths, `private.mask_email` and `private.mask_phone` the only masks, and `directory_reveal` the only debit, checking the balance, inserting the unlock and returning the row in one transaction under `pg_advisory_xact_lock`. Credits are an append only ledger whose balance is `sum(delta)`, never a stored column. An expert is a second buyer shape on `orders` and `invoices` (`buyer_expert_id`, `orders_check_buyer` holding exactly one shape per row), so a credit pack is an ordinary order on the spec 0011 rail: `settle_order` grants `the_order.credits` in the same transaction as `paid`, guarded by the partial unique index on `(order_id) where reason = 'purchase'` so any number of settle retries grant once, and `orders.credits` is frozen at purchase so a resized pack never changes a pending invoice. The expert insert policy checks the package `kind` **and** the `credits` against `packages`, because `orders` has `UPDATE` revoked and that policy is the only guard against an expert minting their own credits. An expert order never enters a delivery state: `private.check_order_transition` raises and `classifyScheduleError` maps the fragment to `not_deliverable`. Every buyer facing alert names the buyer through `buyerLabel` in `src/features/checkout/buyer.ts`, never a direct `organizations` join, because an expert order's `organization_id` is null. Strings live in the `directory` namespace in both catalogs; the three events carry ids and codes only. The per environment checklist (the lawyer's commit, the staging import as the last step, one real purchase and reveal, the Slack alert, the two invoices and the CSV) lives in `docs/directory.md`.
- **Structured assessments follow `docs/assessments.md`** (spec 0019). Questionnaire content is data, never code: `pnpm questionnaires:build` writes `src/features/assessments/content/*.json` from the raw exports in the gitignored `docs/raw/` and `pnpm questionnaires:migration` renders the seed as upserts only, so a rerun changes no row count. Item identity is `position`, never the printed label, and every content text is a `{de, en}` pair whose machine drafted German carries `deReviewed: false` until a person clears it. `questionnaire_versions` and `questionnaire_items` are kind G reference data; `assessments` and `assessment_answers` are kind T with the narrowings written as `DEVIATION` notes at the top of each schema file: a client member never writes either table and never reads an answer at all, an expert writes answers only on their own `draft`, and `authenticated` may update only `status`, `site` and `conducted_on`. An assessment pins its `questionnaire_version_key` for life, so a content correction never moves a past score. Every guard is a trigger, never app code: `private.check_assessment_transition` allows `draft -> submitted` once and refuses an incomplete submit, `private.check_assessment_open` refuses any answer write once the parent is submitted for every role including the service role, and `classifyAssessmentError` in `errors.ts` maps each raised fragment to a typed action error. A section exclusion is an `assessment_answers` row with a null `item_id`, so it autosaves, locks and audits on the same path as a rating; a questionnaire whose catalogue entry sets `allowsSectionExclusion: false` (ISO 45001) answers `not_allowed`. `computeScore` in `model.ts` is the one scoring function in the codebase (feature 18 imports it) and counts only rateable top level items of sections that are not excluded, so an annex sub item rating is stored but never counted. Client and ops status surfaces read the narrow `AssessmentState` from `listAssessmentStates`, which cannot carry a score or a note. Strings live in the `assessments` namespace in both catalogs. `expert_bookings` is a definer view over `orders` exposing no money column, the one place an expert reads an order. The per environment checklist and the German review loop live in `docs/assessments.md`.
- **A server action's success work belongs in the click handler.** `submit` from `useFormAction` (`src/hooks/use-form-action.ts`) resolves with that one dispatch's result, so a toast, a `router.refresh` or closing a dialog goes in the handler that awaited it, never in a `useEffect` watching `result`: `useActionState` holds its last value for the life of the component, so such an effect re-runs on every later render and announces one write several times. Eight older consumers still use the effect shape and are a listed follow up in `docs/scope/index.md`.
- **Authenticated areas are `force-dynamic`**; static rendering only under `(marketing)`. Every user facing string goes through next-intl (`messages/de-CH.json` and `messages/en-CH.json`; the database and the URL use the short codes `de` and `en`, see `docs/localization.md`). The app role lives in `app_metadata.role`, never a top level `role` claim.
- **Accessibility WCAG 2.2 AA**: Biome a11y rules in the editor, axe in Playwright as the second net. No ESLint.
- **Design system**: build all UI to `docs/design.md` (art direction, the component inventory and the build mandate); token values live in `src/app/globals.css`, and every new primitive gets a section on the ops only `/admin/design` gallery so axe scans it. No font weight anywhere goes above 600 and the three `display-*` tokens sit at 450 (owner decision of 2026-09-10): Geist carries a weight axis and no width axis, so weight is the only lever on how heavy a statement sits. `tests/font-weight.test.ts` is the gate, because the ceiling has three spellings (a Tailwind utility, a `font-[700]` arbitrary value and a raw `font-weight`/`fontWeight` declaration) and a review grep misses one; the social card is the one known exception, since `Geist-Bold.ttf` is a static 700 instance and capping it needs a 600 weight font file. The Web Interface Guidelines are a named gate under `## Interface compliance` there: run the `web-design-guidelines` skill against the files you changed before a marketing pull request, the way `pnpm budget` gates first load JavaScript. That section also records the load bearing patterns not to undo and the deliberate exceptions (sentence case over Title Case, real autocomplete tokens on the enquiry form), which are decisions rather than findings.
- **Conventional commit messages** (`feat:`, `fix:`, `chore:`, `docs:`, `test:`).
