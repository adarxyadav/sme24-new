# Review, feat/auth-organizations-roles, 2026-09-05

**Reviewed by**: Claude Opus (author on Claude Fable 5.1)
**Scope**: 75 files, branch vs `main` (merge base 7cc333e): 14 commits; `pnpm-lock.yaml` and `public/` assets skipped
**Verdict**: Changes requested

## Summary

The branch turns spec 0005 into a complete auth surface: password, six digit code and provider sign in, confirmation and reset through one token hash handler, an onboarding page for provider sign ups, a staff invite script, five bilingual email templates, a restructured proxy and a `terms_accepted_at` column with a definer function as its only API write path. The security fundamentals are right and were clearly thought about: `next` validation is genuinely airtight (I tried protocol relative, backslash, encoded slash and userinfo forms, all rejected or resolved back to the app origin), role smuggling is blocked in two independent layers, every "send an email" action answers success for an unknown address, and the confirm handler never answers 500 after a token was accepted. The amendment of 2026-09-05 landed cleanly: one `codeInvalidOrExpired` key, no `codeInvalid` or `codeExpired` left anywhere, and a Vitest case that asserts the absence.

Two findings hold up a merge. `create_organization` is a check then insert with no constraint or lock behind it, and this branch is the first code to call it, from two places where concurrent calls are reachable; the "double submit" test proves the button is disabled, not that the server is safe. And `email_change.html` ships wired into `config.toml` and the hosted checklist while the confirm handler rejects `type=email_change` outright, so the link in that template cannot work. The rest are minors and nits: a second class-merge library added for one component, an error state with no visible message, and two unreachable message keys.

## Major

### 🟠 `ensureOrganization` can create two organizations for one user under a real race, `src/features/auth/session.ts:37`
**Problem**: `create_organization` (`supabase/schemas/11_organization_members.sql:186-220`) guards one organization per user with `if exists (select 1 from public.organization_members m where m.user_id = caller) then raise 'already_member'`, then inserts. `organization_members` has `unique (organization_id, user_id)` and nothing on `user_id` alone (line 14, and the table comment says so deliberately), so nothing stops two concurrent transactions from both passing the `exists` check and both inserting into `organizations` plus `organization_members` with different `organization_id`s. The final `update public.profiles set organization_id = org_id` then races too, so the profile ends up pointing at one of the two while an orphaned organization and a second `owner` membership survive.

This function predates the branch, but the branch is the first code that calls it, and it calls it from two places where concurrency is genuinely reachable rather than theoretical:
- `finalizeSignIn` (`src/features/auth/session.ts:88`) runs it inside `/api/auth/confirm`. A user who double clicks the confirmation button in their mail client, or whose mail client prefetches the link while the user also opens it, produces two in-flight `GET`s against the same token hash. The first `verifyOtp` wins and the second fails, so in that exact case only one reaches `ensureOrganization` — but the same helper also runs from `signIn` and `verifyCode`, and two sign in submits from two tabs of a confirmed-but-not-yet-onboarded account both reach it with valid sessions.
- `completeOnboarding` (`src/features/auth/actions.ts:329`) runs it from a server action. The disabled submit button is a client side guard only; two tabs on `/app/onboarding`, or a replayed action request, bypass it entirely.

**Why it matters**: the spec names this a key invariant ("a client with one organization can never create a second (`create_organization` refuses `already_member`)"), and every kind T table from spec 0002 hangs its tenancy off `profiles.organization_id` plus the `organization_id` claim. A user with two owner memberships and one profile pointer is a tenant boundary in an inconsistent state: the orphaned organization is invisible to the app but real in the database and in the append only audit log, and the `already_member` branch in `ensureOrganization` will thereafter mask the inconsistency as success forever. Cleaning it up later means a data migration, not a code fix. The e2e test at `e2e/auth.spec.ts:369-372` clicks submit twice, but the second click is `force: true, noWaitAfter: true` against an already-disabled button in the same browser — it exercises the client guard, not two concurrent server requests, so it will keep passing whatever the server does.

**Suggested fix**: make the invariant hold in the database rather than in the check. The cheapest correct option is a transaction scoped advisory lock keyed on the caller at the top of `create_organization` (`perform pg_advisory_xact_lock(hashtextextended(caller::text, 0))`) before the `exists` check, so the second transaction blocks and then sees the first one's row and raises `already_member` as intended. A partial unique index on `organization_members (user_id)` would also close it and is the stronger guarantee, but the table comment says multi organization users are a deliberate future, so the advisory lock is the change that respects that. Either way, add a pgTAP or Vitest case that runs two `create_organization` calls for the same caller concurrently and asserts exactly one organization exists.

### 🟠 The `email_change` template ships a link the confirm handler rejects, `src/app/api/auth/confirm/route.ts:13`
**Problem**: `supabase/templates/email_change.html` builds its link as `.../api/auth/confirm?token_hash={{ .TokenHash }}&type=email_change&next={{ .RedirectTo }}`, and `supabase/config.toml` wires that file into `[auth.email.template.email_change]`. But `LINK_TYPES` is `["signup", "magiclink", "email", "recovery", "invite"]`, so `isLinkType("email_change")` is false and line 53 short circuits to `expired("email_change")` before `verifyOtp` is ever called. `email_change` is a first class `EmailOtpType` in the installed `@supabase/auth-js@2.112.4` (`'signup' | 'invite' | 'magiclink' | 'recovery' | 'email_change' | 'email'`), so the token would verify fine — the handler simply refuses to look at it.

It gets worse on the way out: `expired("email_change")` redirects to `/de/sign-in?error=link_expired&type=email_change`, and `LINK_EXPIRED_TYPES` in `src/features/auth/notices.ts:9` does not contain `email_change` either, so `isLinkExpiredType` fails and `noticeFrom` (`src/app/[locale]/sign-in/page.tsx:23`) falls back to `"signup"`. The user is told their *signup* link expired and is offered a confirmation resend button that has nothing to do with the email change they asked for.

**Why it matters**: `docs/auth.md` instructs the operator to paste this file into the Change email template on staging and prod, and `double_confirm_changes = true` is already set, so the moment anyone changes an address — from Studio today, from the account settings page the spec lists as a follow up tomorrow — both confirmation mails carry a dead link and a misleading error. The failure is silent from the app's side: the log line at route.ts:61 never runs because `verifyOtp` never runs, so there is no signal that the type was rejected rather than the token. Spec build plan item 13 calls this template "for completeness", but completeness that ships wired into the config and the hosted checklist is a shipped feature, and a `Never returns a 500 after a successful verification` contract does not help when the verification is skipped.

**Suggested fix**: add `email_change` to `LINK_TYPES` in the confirm handler and to `LINK_EXPIRED_TYPES` in `notices.ts`, give it a `linkExpired.emailChange` string in both catalogs, and decide its success branch explicitly — it belongs with `recovery` and `invite` (redirect to `next`, do not run `finalizeSignIn`) since an email change should not re-land the user as if they had just signed in. If instead the intent is that no email change flow exists yet, remove the template and its `config.toml` block and drop it from the `docs/auth.md` checklist, so nothing paste-able points at a handler that will not serve it. Cover whichever branch you keep with an `errors.test.ts` style assertion that every `type` a template can emit is accepted by `isLinkType`.

## Minor

### 🟡 A second class-merge implementation entered the tree for one component, `src/components/ui/input-otp.tsx:3`
**Problem**: `input-otp.tsx` does `import { cn } from "cn"` and `package.json` gained `"cn": "^0.2.5"` to satisfy it. Every one of the other 26 primitives in `src/components/ui/` imports `cn` from `@/lib/utils`, which is `twMerge(clsx(inputs))` over the project's pinned `tailwind-merge`. The `cn` package is legitimate (`shadcn-ui/cn`, a compiled clsx + tailwind-merge replacement) and this is almost certainly what the shadcn CLI emitted rather than a deliberate choice, but the result is two independent class merge engines in one bundle with different conflict resolution tables.

**Why it matters**: `tailwind-merge`'s conflict groups are version specific data. Two engines mean a class pair that resolves one way in `Button` can resolve the other way in `InputOTPSlot`, and the divergence appears only when a caller passes a `className` that collides with the base — exactly the override path `InputOTPSlot` exposes. It also adds a dependency and its transitive tree to the bundle for a function the repo already has, and it quietly breaks the "one primitive style" premise the design system rests on. Neither Biome nor `pnpm typecheck` will ever flag it.

**Suggested fix**: change the import to `@/lib/utils` and drop `cn` from `package.json` and the lockfile. Nothing else in `input-otp.tsx` depends on the package's extra exports. If a future shadcn add re-introduces it, a Biome `noRestrictedImports` rule on `"cn"` would make it fail the check job instead of landing silently.

### 🟡 The empty email guard marks the field invalid with no message, `src/features/auth/ui/sign-in-form.tsx:119`
**Problem**: `withEmail` does `form.setError("email", { type: "required", message: undefined })` when the user presses "Email me a code instead" (or a `link_expired` resend) with an empty email field. `message: undefined` flows into `errorText` → `issueMessage`, which returns `undefined` for a falsy message, and `FieldError` renders `null` when it has neither `children` nor `errors` (`src/components/ui/field.tsx:174-181`). The field gets `aria-invalid="true"` and `aria-describedby="email-error"` pointing at an element that is empty, and focus moves there — with nothing said about why.

**Why it matters**: WCAG 2.2 AA 3.3.1 (Error Identification) requires the error to be described in text, and 1.3.1 is stretched by an `aria-describedby` that resolves to empty content — a screen reader user gets a focus move and an "invalid" state with no explanation, and a sighted user gets a focus ring on an empty field. This is the one error path on the sign in page that produces no text, and axe will not catch it: `expectNoAxeViolations` in `e2e/auth.spec.ts:55` scans the page as rendered, and no test ever presses the code button with an empty field, so the state is never on screen when axe looks.

**Suggested fix**: pass a real message key. `auth.validation` has no "email required" entry yet, so either add one (`emailRequired`) and set `message: "emailRequired"`, or route the secondary actions through `form.trigger("email")` so Zod's own localized required/invalid-email message is produced by the same path the submit button uses. Then add an e2e assertion that pressing the code button with an empty email shows visible text, so the state is in front of axe.

### 🟡 `ensureOrganization` branches on substring matches of a free text error message, `src/features/auth/session.ts:38-39`
**Problem**: the two control flow decisions that matter — treat as success, or report `not_a_client` — are `error.message.includes("already_member")` and `error.message.includes("not_a_client")`. PostgREST puts the `raise exception` text into `message` today, so this works, but it is a string contract with no test pinning it, spread across the one function the spec names as the only caller of `create_organization`.

**Why it matters**: `already_member` mapping to success is what makes a retried confirmation idempotent (spec key invariants), and `not_a_client` mapping to `/forbidden` is an authorization decision. If a PostgREST or Supabase upgrade moves the raise text to `details` or `hint`, or prefixes it, both silently degrade: `already_member` starts returning `{ ok: false, error: "failed" }`, which sends a user who *does* have an organization to `/app/onboarding` in a loop the proxy will bounce back, and `not_a_client` degrades to the generic message instead of `/forbidden`. Nothing in the suite would notice — `e2e/auth.spec.ts` never provokes either error from the RPC.

**Suggested fix**: raise the two conditions with SQLSTATEs the function owns (`raise exception 'already_member' using errcode = 'P0001'` style, or distinct custom codes) and branch on `error.code` instead of the message, keeping the message only for the log line. Failing that, add a pgTAP case asserting the exact message text of both raises, so a change to the contract fails the `database` job rather than production.

### 🟡 A silent Supabase code on `verifyOtp` is reported as a wrong code, `src/features/auth/actions.ts:159`
**Problem**: `verifyCode` calls `failure(error, "verify-code")`, and when `failure` decides the code is silent (`otp_disabled`, `user_already_exists`, `email_exists`) it returns `{ ok: true }`. The caller then does `result.ok ? { ok: false, error: "codeInvalidOrExpired" } : result` — so a silent code is turned back into a visible error. The same inversion appears nowhere else; `signUp`, `requestCode`, `resendConfirmation` and `requestPasswordReset` all map a silent code to their real success shape.

**Why it matters**: it is defensible as written (none of the three silent codes should reach `verifyOtp`, and showing the code error is the safe fallback), but the expression reads as a copy of the sign in pattern at line 182 where the inversion is deliberate, and it means `failure`'s silent branch has two opposite meanings depending on the call site. If Supabase ever answers `otp_disabled` for a verification against a provider-only account, the user is told their code is wrong rather than being told anything true.

**Suggested fix**: skip `failure`'s silent branch here by checking `isKnownAuthError`/`authErrorKey` directly, or add a one line comment stating that a silent code is impossible on this call and the fallback is deliberate. A Vitest case over the three silent codes through `verifyCode`'s mapping would pin whichever you choose.

## Nits

- ⚪ `src/features/auth/errors.ts:18`, `notAClient` is in `AUTH_ERROR_KEYS` and has a message in both catalogs, but no action ever returns it — `completeOnboarding` redirects to `/forbidden` on `not_a_client` instead (`actions.ts:331`). Dead key and dead string.
- ⚪ `messages/de-CH.json` / `messages/en-CH.json`, `auth.linkExpired.email` is unreachable: the sign in form maps both `magiclink` and `email` to the `code` string (`sign-in-form.tsx:155`), so the `email` entry is never rendered.
- ⚪ `messages/de-CH.json`, `auth.inbox.enterCode` has no caller anywhere in `src/`.
- ⚪ `supabase/templates/*.html:1`, every template declares `<html lang="de">` while carrying an English half in a `lang="en"` cell. The cell attribute is right, but the confirmation and magic link templates put the code block in both halves, so a screen reader reads the same six digits twice.
- ⚪ `src/features/auth/ui/sign-in-form.tsx:71`, `(expiredType && resendActionFor(expiredType)) ?? resendConfirmation` passes `resendConfirmation` as the placeholder for the invite case, where the button is never rendered. Harmless, but a no-op action would say the intent more plainly than the wrong one.
- ⚪ `src/app/api/auth/confirm/route.ts:53`, `expired(type ?? "signup")` reports a missing or unknown `type` as a failed signup link, so a mangled URL offers a confirmation resend. A distinct default (or no `type`) would avoid telling the user something specific and wrong.
- ⚪ `src/features/auth/ui/inbox-notice.tsx:33`, the `resend ?? (async () => ({ ok: true, data: { email } }))` fallback is only reached when `resend` is absent, in which case the button that would dispatch it is not rendered either. The hook could take `resend` and simply not dispatch.
- ⚪ `supabase/templates/confirmation.html`, the copy says the code and link are "24 Stunden gültig" / "valid for 24 hours" while `otp_expiry = 900` sets 15 minutes. `magic_link.html` and `recovery.html` both say 15 minutes correctly. Supabase does use a longer window for the signup confirmation link than for the OTP, so the sentence is half right — but it covers "Beides" / "Both", and the code half is wrong by 95x.

## Strengths

- The `next` validation is the best part of the branch. `resolveNext` checks origin and locale prefix before anything else, `nextWithinLocale` rejects protocol relative and backslash forms, and the same rule genuinely lives in one place shared by the proxy, the actions and both handlers. I probed it with `//evil.com/de/app`, `/de\evil.com`, `%2f%2f` and userinfo forms; every one either resolves back to the app origin or falls through to the role home. The `landingPath` fallback means there is no path where a bad `next` produces anything but a safe redirect.
- Role smuggling is closed twice over and both layers are tested: `handle_new_user` whitelists the enum, the access token hook strips and rewrites `app_metadata.role` unconditionally including the no-profile case (with a comment explaining exactly why the `else` branch exists), and `e2e/auth.spec.ts:176-199` posts a raw signup with `app_metadata.role: "ops"` against the real endpoint and asserts the profile comes back `client`. That is the right shape of test for that claim.
- The address-enumeration discipline is consistent and deliberate: `SILENT_CODES` covers `otp_disabled`, `user_already_exists` and `email_exists`, every email-sending action folds them into success, `inbox.code` and `inbox.reset` are worded conditionally ("falls ein Konto besteht"), and two e2e tests assert `noMailFor` rather than just checking the UI text. The one documented exception (unconfirmed, which needs the right password) matches AC-12 exactly.
- `accept_terms()` is a textbook definer function: `search_path = ''`, an `auth.uid()` null check before any write, `where terms_accepted_at is null` so it is idempotent, a `no_profile` raise so it can never return null on success, and `revoke ... from anon, public` re-added by hand in the migration exactly as AGENTS.md warns. `supabase/tests/accept_terms.test.sql` then asserts the column grant, the direct-update refusal in both directions, the null-only write, the second-call behaviour and the anon refusal — 16 assertions that all test real behaviour, not shape.
- `redirectKeepingCookies` in the proxy, and the comment explaining it, is the kind of detail that is normally found in production: with rotation, dropping the refreshed cookies on a redirect hands the browser a spent token. Two proxy tests assert the cookies survive both the forbidden and the onboarding redirect.
- The confirm handler's "never 500 after a verified token" contract is implemented, not just claimed: the `try`/`catch` around `finalizeSignIn` captures to Sentry and still lands the user somewhere sensible based on their role.
- `e2e/db.ts`'s `deleteAccount` keying cleanup on `created_by` rather than the profile pointer, with the comment explaining which failure mode it covers, plus the `sweep.ts` global setup and teardown, is unusually careful test hygiene for a suite this young.

## Test coverage

Good, and better than the average for a feature this size. What is genuinely covered: the proxy rules including every auth page bounce, the onboarding rule in both directions, the staff exemption and cookie preservation (`tests/proxy.test.ts`, 11 cases); the error map including the amendment's combined key and the absence of the two dropped keys (`tests/features/auth/errors.test.ts`); the consent column contract end to end in pgTAP; and the real flows in `e2e/auth.spec.ts` — password sign up through Mailpit with a fresh browser context, code sign up and sign in, wrong code, unconfirmed sign in, reset with a second context proving revocation, sign out cookie clearing, token refresh with a second navigation, the invite script end to end, and axe over eleven auth URLs.

Gaps worth naming:
- **The concurrency claim is untested** (Major 1). `e2e/auth.spec.ts:369-372` is a double click on a disabled button in one browser; it cannot fail if the server is racy. A test that fires two `create_organization` calls concurrently for one caller is the missing piece.
- **`email_change` is untested** (Major 2), which is how a template wired into `config.toml` shipped pointing at a handler that rejects it. A cheap guard is a unit assertion that every `type=` string appearing in `supabase/templates/*.html` passes `isLinkType`.
- **`finalizeSignIn` has no unit tests** despite being the branching heart of the feature — five outcomes (no user, unverified email, staff, client with org, client without org and its metadata sub-branch) reachable from four call sites, all covered only indirectly through Playwright. The unverified-provider-email branch (`session.ts:69-73`) in particular has no coverage at all, local or e2e, since providers cannot run on the local stack.
- **`signInWithProvider` and `/api/auth/callback` are untested by anything automated** — AC-5 is explicitly hand-verified on staging, which the spec accepts, but the `next` construction at `actions.ts:200-202` and the callback's error branches are pure functions of their input and could be unit tested without a provider.
- **`updatePassword`'s no-session branch** (`actions.ts:279-281`) and the `signOut({ scope: "others" })` failure path (line 289-292) are never exercised.
- The `verify.md` checklist honestly leaves two boxes unticked (staging providers, prefilled company name), which is the right way to record it.
