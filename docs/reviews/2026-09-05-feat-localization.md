# Review, feat/localization, 2026-09-05

**Scope**: 78 files, branch vs `origin/main` (merge base e12da78): 77 committed across 11 commits plus one uncommitted scope tick in `docs/scope/foundations.md`; `pnpm-lock.yaml` and `public/` assets skipped
**Verdict**: Approve with nits

## Summary

The branch turns spec 0001's locale routing into a real localization foundation: `de-CH`/`en-CH` behind `/de` and `/en` derived from a single `LOCALE_CODE` table, named Swiss formats with a pinned `Europe/Zurich` timezone, a typed route map, typed catalogs with a TypeScript-AST literal scanner, a standalone translator for tasks, a stored language on `profiles` and `organizations` with the migration and pgTAP, localized Zod messages, language alternates and a bilingual sitemap. This is careful, disciplined work: every one of the 13 acceptance criteria is implemented and covered by a test that asserts real behaviour, the two-spelling invariant is genuinely single-sourced, and `docs/localization.md` is a working reference rather than a summary. I found no blockers and no majors. The findings below are small resilience and hygiene gaps that will not bite in the first month but are cheap to close now.

## Minor

### 🟡 An unhandled rejection in `setLocale` silently cancels the language switch, `src/components/shell/locale-menu-items.tsx:52-55`
**Problem**: `onSelect` is `await setLocale(...)` followed by `router.replace(...)`, with no `catch`. A server action can reject for reasons that have nothing to do with the write: an offline browser, a redeployed action id, a 500 from the Next runtime. When it rejects, `router.replace` never runs, so the user clicks "English" and the page stays German with no feedback, and React logs an unhandled rejection that the browser Sentry client will report as an error.
**Why it matters**: the switch is the only way a signed-in user changes language. The spec is explicit that the URL is the truth for the page and the profile "only feeds what leaves the app" (AC-2, and the JSDoc on the action repeats it), so a failed persist should never block the navigation. Today it does. `tests/shell/locale-switchers.test.tsx:129-138` covers exactly this scenario for `LocaleSwitcher` but the equivalent case for the menu is untested, which is why it slipped through.
**Suggested fix**: wrap the await so a rejection is swallowed (or logged) and `router.replace` runs unconditionally — a `try/finally`, or `await setLocale(...).catch(() => {})`. Then add the mirror of the existing `LocaleSwitcher` failure test: mock `setLocale` to reject and assert `router.replace` was still called once with the target locale.

### 🟡 `void setLocale(...)` on the marketing links produces an unhandled rejection, `src/components/locale-switcher.tsx:56-58`
**Problem**: `onClick` fires `void setLocale({ locale: LOCALE_CODE[target] })`. `void` discards the value, not the rejection. On a network failure the promise rejects with no handler, which surfaces as an `unhandledrejection` and is captured by the Sentry browser SDK.
**Why it matters**: this switcher sits on every public page and the sign-in page, so a flaky network turns a best-effort write into recurring Sentry noise from the highest-traffic surface in the app. The design intent is correct (best effort, the link carries the switch), the failure path just is not closed. `tests/shell/locale-switchers.test.tsx:129` mocks a rejection and asserts the href survives, but Vitest will not fail on an unhandled rejection from a `void`ed promise, so the test passes without proving anything about the rejection.
**Suggested fix**: attach a no-op or logging `.catch()` instead of `void`, and assert in the existing failure test that no unhandled rejection is raised (`vi.spyOn` on the rejection handler, or simply assert the `.catch` path was taken).

### 🟡 `on-error.ts` imports `@sentry/node` inside the Next.js app runtime, `src/i18n/on-error.ts:1`
**Problem**: every other module under `src/` outside `src/trigger/` imports `@sentry/nextjs` (`src/instrumentation.ts`, `sentry.server.config.ts`, `src/features/scaffold/actions.ts`, `src/components/shell/area-error.tsx`). `on-error.ts` imports `captureException` from `@sentry/node`, and it is loaded by `src/i18n/request.ts`, which is the Next.js request config — squarely inside the app runtime, not the task runtime.
**Why it matters**: it works today only because both packages resolve to the same `@sentry/core@10.73.0` instance and therefore the same global client (I verified this in `node_modules`). That is an implementation detail, not a contract. A pnpm hoist change, a version bump that splits the two, or Sentry's Next.js webpack plugin instrumenting the `@sentry/nextjs` entry differently would silently drop every `MISSING_MESSAGE` report in production — the exact failure mode AC-12 exists to prevent, and one that produces no error of its own.
**Why it is not a Major**: the choice is deliberate and constrained. `on-error.ts` is shared with `src/i18n/standalone.ts`, which `src/trigger/scaffold-check.ts` bundles with Trigger.dev's esbuild, where `@sentry/nextjs` would not build. `@sentry/node` is the only import that works in both.
**Suggested fix**: make the coupling explicit rather than incidental. Either inject the capture function (the request config passes the `@sentry/nextjs` one, the standalone factory passes the `@sentry/node` one, `on-error.ts` takes it as a parameter), or leave the import and add a one-line comment naming the shared-core assumption so a future dependency bump has something to trip over. A test that asserts a production `MISSING_MESSAGE` reaches the *configured* client (not the mocked module) would also catch a split.

### 🟡 `reportedKeys` and the Sentry fingerprint key on the full error message, not the message key, `src/i18n/on-error.ts:32,36`
**Problem**: `const key = error.message` uses next-intl's whole sentence (`` Could not resolve `nav.nope` in messages for locale `de-CH`. ``), not the key path. Two consequences: the same missing key in `de-CH` and `en-CH` is reported twice, and for `INVALID_MESSAGE` the message can embed the offending ICU fragment, so a message with variable content produces one Sentry group per variant.
**Why it matters**: AC-12 specifies "once per key per process" and "the Sentry fingerprint only groups". Both are off by the locale dimension, and `INVALID_MESSAGE` can defeat grouping entirely — the opposite of what the guard is for. The set is also unbounded, which is harmless while the input is a bounded catalog but not if a variable-content message reaches it.
**Suggested fix**: extract the key path from `error.message` (next-intl puts it in backticks) or fall back to a normalised form, and use that for both the set and the fingerprint. Keep the full message in the captured event so nothing is lost. The existing test at `tests/i18n/on-error.test.ts:43` already exercises two distinct keys and would extend naturally to two locales of one key.

### 🟡 The e2e sidebar test leaves the seeded ops profile mutated, `e2e/localization.spec.ts:76-79`
**Problem**: `supabase/seed.sql:53` seeds `ops@example.com` with `locale: "en"`. The test switches the profile to `en`, then to `de`, and ends there — so after one e2e run the seeded state no longer matches `seed.sql`.
**Why it matters**: no suite depends on it today (`e2e/helpers.ts:16` always signs in through `/de/sign-in`, so the URL decides the language), which is why this is Minor and not Major. But it is a test that mutates shared fixture state and does not restore it, and the comment on line 76 asserts the opposite of what the seed says. The next feature that reads a seeded profile locale will get a flake whose cause is two files away.
**Suggested fix**: restore `en` rather than `de` (matching the seed), or better, give the test its own user so it never touches shared fixture state. At minimum correct the comment, which currently records a wrong reason for the right-looking action.

### 🟡 `MARKETING_ROUTES` accepts dynamic routes that `absoluteUrl` cannot resolve, `src/i18n/pathnames.ts:25`
**Problem**: the type is `readonly Pathname[]`, so any key of `PATHNAMES` is assignable — including a template route such as `"/app/companies/[id]"` once one exists. `src/app/sitemap.ts:11` and `src/i18n/metadata.ts:17` then call `getPathname({ href: route, locale })` with no `params`, which cannot produce a real URL.
**Why it matters**: the spec anticipates this exactly ("feature 13 adds its pages and their German slugs"), and the failure would be a sitemap full of literal `[id]` segments rather than a type error or a crash — a silent SEO defect. `tests/i18n/routing.test.ts:107` only asserts every marketing route is a key of the map, which a dynamic route also satisfies.
**Suggested fix**: narrow the element type to the static routes, e.g. a conditional type excluding keys containing `[`, so a dynamic route in `MARKETING_ROUTES` fails `pnpm typecheck` the moment feature 13 adds one.

### 🟡 `AGENTS.md` still names the pre-rename catalog files, `AGENTS.md:52`
**Problem**: the rule reads "Every user facing string goes through next-intl (`messages/<locale>.json`, `de` and `en`)". The files are now `messages/de-CH.json` and `messages/en-CH.json`, and the `de`/`en` spelling is specifically the *database and URL* form, which is the one distinction this whole feature exists to keep straight.
**Why it matters**: `AGENTS.md` is the canonical context every later `/develop` run reads. This line now teaches the wrong half of the two-spelling rule, in the one document most likely to be trusted without checking.
**Suggested fix**: update the line to `messages/de-CH.json` and `messages/en-CH.json`, and point at `docs/localization.md` for the short-code distinction. (Worth doing in this branch rather than leaving it to `/sync`, since the branch is what introduced the drift.)

## Nits

- ⚪ `tests/i18n/literal-allowlist.ts:27`, `/^[A-Z]{2}$/` is commented "canton codes" but allows any two-letter uppercase literal anywhere in the tree (`OK`, `NO`, `ID`). Scoping it to the actual canton list, or to the file that renders them, keeps the allow list as reviewable as its own docstring claims.
- ⚪ `src/i18n/standalone.ts:7-9`, `loadMessages` interpolates `locale` straight into a dynamic import. Every caller today reaches it through `localeFromCode`, so the value is always valid, but the function is exported and its only guard is the type. One `isLocale` check would make it safe for the email templates feature 7 will add.
- ⚪ `src/features/auth/actions.ts:44-46`, `nextRedirect(next)` accepts any same-origin path starting with `/de/` or `/en/`, including traversal forms like `/de/..//evil.com` (which resolves to `https://sme24.ch//evil.com` — same origin, so not an open redirect, but not a route either). The previous code went through the typed `redirect()`. Normalising with `new URL(next, origin).pathname` before redirecting would restore the guarantee that `next` names a real path.
- ⚪ `src/i18n/on-error.ts:52-54`, `resetReportedKeys` is a test-only export in production code. Harmless and honestly labelled, but a `__resetForTests` naming convention or a Biome comment would keep it from being called by mistake.
- ⚪ `src/components/ui/chart.tsx:255`, `format.number(item.value)` uses the unnamed default rather than one of the named formats. Correct for a generic chart value, but the spec's invariant ("nothing calls `Intl` or `toLocaleString` directly") is about to be read by later features as "always use a named format" — a one-line comment saying why the default is right here would prevent a wrong "fix".

## Strengths

- **The two-spelling invariant is genuinely single-sourced.** `LOCALE_CODE` is the only table, the URL prefixes are derived from it (`src/i18n/routing.ts:49-52`), `localeCodeSchema` derives from `Object.values(LOCALE_CODE)` (`src/features/localization/schema.ts:5`), and `tests/i18n/routing.test.ts:29-38` asserts the derivation rather than restating the constants. This is the hardest part of the feature to keep honest and it is done properly.
- **The format tests pin the exact ICU output, invisible characters included.** `tests/i18n/formats.test.ts:15,66-69` encodes the U+00A0 currency separator and asserts `charCodeAt` on the U+2019 grouping apostrophe, and runs every assertion through both the request formatter and the standalone one. A future ICU or Node bump will fail loudly instead of quietly shipping `CHF 4'900.00`.
- **The literal scanner is a real gate, not a regex.** `tests/i18n/literals.test.ts` parses each `.tsx` with the TypeScript compiler and distinguishes user-facing expression containers from `className={...}` by inspecting the parent node (`isUserFacingContainer`, line 40). The failure message names file, line and text and tells the author where to put the string. Empty `ALLOWED_FILES` at this stage is a good sign.
- **The query-preserving switch is tested at the level that actually breaks.** `tests/shell/locale-switchers.test.tsx:89-99` uses a repeated query key (`tab=a&tab=b`) — the case `searchParamsToQuery` exists to handle — and line 189 asserts the *call order* of `setLocale` before `router.replace`, which is the whole point of awaiting in the menu.
- **The migration re-derives cleanly from the schema files.** The `create_organization` body and the owner-column trigger in `supabase/migrations/20260904181855_add_organization_locale.sql` match `supabase/schemas/11_organization_members.sql` and `10_organizations.sql` character for character, `CREATE OR REPLACE` preserves the existing grants, and the `ADD CONSTRAINT` lands after the defaulted column so no existing row can violate it. The pgTAP additions cover the copy-from-profile path, the owner update, the plain-member refusal and the check constraint (`plan(14)` and `plan(18)` both match the assertion counts).
- **`docs/localization.md` is written for the next author, not for the reviewer.** The two-spellings table, the glossary with usage notes ("Kundenunternehmen in the shell, Organisation in settings"), and the explicit warning that a nested provider *replaces* rather than merges are the things that would otherwise be relearned by bug.

## Test coverage

Coverage is proportionate and behaviour-focused. Every acceptance criterion has at least one test that would fail if the behaviour regressed:

- **Covered well**: the locale table and its derivations (`tests/i18n/routing.test.ts`, AC-1/AC-13); the exact format strings through both formatters plus the timezone and the ICU apostrophe (`tests/i18n/formats.test.ts`, AC-3); catalog parity (`tests/messages.test.ts`, AC-4); the literal scan (`tests/i18n/literals.test.ts`, AC-5); the client-bundle split at both the unit level (`tests/i18n/client-messages.test.ts`) and, correctly, end to end in the real HTML (`e2e/localization.spec.ts:49-55`, AC-6); the standalone translator including the shared throw-in-test behaviour (`tests/i18n/standalone.test.ts`, AC-7); the stored-locale queries with the missing-row fallback and the throw-on-error path (`tests/localization/queries.test.ts`, AC-7); `setLocale` across all four outcomes (`tests/localization/set-locale.test.ts`, AC-2); localized Zod messages plus the explicit assertion that the global config is untouched (`tests/lib/validation.test.ts:44-52`, AC-8); the proxy redirects in both languages including the `app_metadata.role` gate (`tests/proxy.test.ts`, AC-13); the alternates and sitemap (`tests/i18n/metadata.test.ts`, AC-10); the once-per-key Sentry guard (`tests/i18n/on-error.test.ts`, AC-12); the task's locale resolution and translated summary (`tests/trigger/scaffold-check.test.ts`, AC-7); and the database rules in pgTAP (AC-9). Playwright adds English axe coverage, the query-preserving switch, the `/de-CH` 404 guard and a real-browser CHF assertion (AC-11).

- **Gaps worth closing** (all listed above as Minors): the `LocaleMenuItems` rejection path is untested while its `LocaleSwitcher` twin is (`tests/shell/locale-switchers.test.tsx:129`); the `LocaleSwitcher` rejection test asserts the href survives but cannot observe the unhandled rejection it triggers; and nothing asserts that a production `MISSING_MESSAGE` reaches the *configured* Sentry client rather than the mocked `@sentry/node` module, which is the assumption the `@sentry/node` import rests on.

- **No test asserts anything meaningless.** The mocks stop at genuine system boundaries (the Supabase client, the Trigger.dev SDK, next-intl's middleware, `next/navigation`) and every assertion is on observable output — rendered text, `href` attributes, the row actually inserted, the exact ICU string. `tests/trigger/scaffold-check.test.ts` in particular fakes the service client rather than the query builder's return values, so it tests what the task writes rather than what it calls.

Verify-step observations weighed and not raised as findings: Zod's German built-in email wording ("Ungültig: E-Mail-Adresse") is odd for a Swiss product but AC-8 explicitly accepts built-in messages and the custom rules read well — a catalog concern for feature 6, not a defect here. The PGRST303 clock-skew warning and the stale-refresh-token noise predate this diff and the proxy already returns cleanly when `getClaims` yields no claims (`src/proxy.ts:24-38`). Node 25 versus the pinned Node 22 is a real divergence, but the formats module deliberately avoids `dateStyle` for exactly that reason (`src/i18n/formats.ts:10-13`) and CI runs Node 22, so the pinned strings are checked on the deployment runtime.
