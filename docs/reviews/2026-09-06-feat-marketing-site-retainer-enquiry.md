## Minor

### 🟡 Cursor `created_at` value is filter-string-interpolated without character restriction, `src/lib/supabase/cursor.ts:36-38`
**Problem**: `afterCursorFilter` builds a raw PostgREST `or=` filter string by directly interpolating `cursor.createdAt` into `created_at.lt.${cursor.createdAt},and(created_at.eq.${cursor.createdAt},id.lt.${cursor.id})`. `decodeCursor` validates `id` against a strict UUID regex, but only validates `createdAt` with `Number.isNaN(Date.parse(createdAt))`, which does not reject characters PostgREST's filter grammar treats specially (commas, parentheses, dots). `Date.parse` is lenient enough that a crafted string could parse successfully while also breaking out of the intended filter clause.
**Why it matters**: The `cursor` query parameter on `/admin/enquiries` is user-controlled (a URL parameter an ops user, or anyone probing the URL before being redirected, can edit). In practice the page is gated by the proxy and by RLS (ops read every row anyway, so the practical blast radius here is limited to malforming ops's own already-fully-visible query, not privilege escalation), but the pattern generalizes: `/admin/emails` shares this same `afterCursorFilter` helper, so any list gated more narrowly in the future inherits the same laxity. Worth tightening now while the surface is still small.
**Suggested fix**: Validate `createdAt` in `decodeCursor` against a strict ISO-8601 timestamp pattern (or re-serialize `new Date(createdAt).toISOString()` and compare) before accepting it, the same way `id` is checked against `UUID_PATTERN`.

### 🟡 `updateEnquiry`'s conditional handler-assignment update swallows its own error silently on the no-op path, `src/features/enquiries/actions.ts:49-61`
**Problem**: When `leavesNew(status)` is true, the first `update(...).eq("id", id).eq("status", "new")` runs and its error is checked (`if (error) return reportFailure(...)`), which is correct. But when that first update matches zero rows (the common case: the row was already `contacted` or `closed`), Supabase returns `{ error: null, data: [] }` with no way to distinguish "row already moved past new" from "row does not exist" — the code proceeds to the second update either way, which is fine functionally (the second update's `.maybeSingle()` catches the not-found case), but the two round-trips mean a genuinely missing id still performs a wasted UPDATE before answering `not_found`. Not a correctness bug, but worth a comment since a future reader may assume the first update's silence implies the row was found.
**Why it matters**: Low impact today (a wasted no-op UPDATE against a nonexistent id), but if the first statement is ever changed to use `.select()` or otherwise treat "0 rows updated" as meaningful, the current code has no signal to distinguish the two cases.
**Suggested fix**: A one-line comment at the first update noting that a zero-row match is expected and harmless (either the target status is already active or the id doesn't exist, both handled by the second statement) would remove the ambiguity for the next reader. Not blocking.
