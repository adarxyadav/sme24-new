## Summary

Feature 10 lets a client hand-enter the eight safety KPIs as ordinary `company_kpis` rows with `source 'client'`, using a read-then-write path around the partial unique index, deleting to clear, and queuing `benchmark-company` under two distinct idempotency keys. The implementation matches the spec closely: the year rules in `years.ts` are pure and well tested across the New Year boundary, the schema's dirty-value normalization prevents an untouched research value from being silently copied into a client row, the actions follow the one-error-handling-pattern convention exactly (typed result, never throw, `forbidden`/`not_found`/`conflict`/`unexpected` all reached and tested), and the AC-1 placement rule (after the table / after the failed alert / after progress, mutually exclusive) is implemented correctly in the page. Test coverage is thorough at every layer (schema table tests, year-boundary tests, action tests against a mocked Supabase client covering the update-returns-zero-rows `forbidden` path and the `23505` `conflict` path, a component test asserting only dirty fields are sent, the pgTAP creator-scoped update assertion, and an e2e spec that seeds research rows and drives the full prefill/save/correct/clear/older-year flow with axe). No blockers or majors found.

## Minor
### 🟡 Spec says `dirtyFields`, code implements its own diff, `src/features/self-assessment/ui/kpi-form.tsx:82-90` and `:119-125`
**Problem**: AC-4 and the "Value sourcing" table in the spec both state the browser sends only changed fields via "`react-hook-form` `dirtyFields` against the prefilled values." The implementation instead wraps the zod resolver with a hand-rolled `changedValues()` that string-compares each field's current text against a `prefilled` ref, and never reads `form.formState.dirtyFields`.
**Why it matters**: Not a functional bug — the outcome (only fields that differ from the prefilled value are sent, a blanked field is a no-op) is achieved and is well tested (`prefillValues`/`changedValues` unit tests, the "sends only the changed fields" and "treats a blanked prefilled field as untouched" component tests, the e2e flow). It is arguably more robust than RHF's `dirtyFields`, which can go stale across the `form.reset(..., { keepDirtyValues: true })` calls this form does on year change and on a `rows` refresh. But a future reader who trusts the spec's mechanism description over the code will be confused, and `/document` or `/sync` may propagate the same inaccurate description.
**Suggested fix**: Update the spec (or a short code comment) to describe the actual mechanism — a value-diff against the last prefilled snapshot, not RHF's dirty-field tracking — so the two stay in sync.

## Strengths
- The read-then-write path around the partial unique index is exactly as risky as the requester flagged, and it is handled correctly: the update loop returns `forbidden` the moment any update affects zero rows (before the insert runs), the insert's `23505` maps to `conflict`, and both branches are directly exercised in `tests/features/self-assessment/actions.test.ts` with a mocked Supabase client that models the real RLS-filtered-zero-rows behavior.
- `years.ts`'s `currentYear` reading the Zurich zone via `Intl.DateTimeFormat` (not `getUTCFullYear`) is correct and is proven at the boundary (`2026-12-31T23:30:00.000Z` → 2027) rather than just asserted.
- The two idempotency keys are exactly as specified (`benchmark/kpis/<companyId>/<max updated_at of the writes>` and `benchmark/kpis-clear/<deleted row id>`), and the "moments" collection correctly gathers `updated_at` from both the update and insert results before taking the max.
