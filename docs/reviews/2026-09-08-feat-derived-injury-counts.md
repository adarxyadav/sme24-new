## Summary

Feature 27 (spec 0012) adds a display-only `derived` block to the benchmark snapshot: an expected yearly lost-time injury count and recordable injury count, computed from the same exposure helper the CHF cost line already used, shown with an outline "Calculated" badge and a provenance line. The load-bearing safety step — restructuring `SNAPSHOT_SCHEMAS` to literal version keys before bumping `MODEL_VERSION` to `benchmark-model@2` — is done correctly: `@1` stays unwidened and reachable, a `@1` row's blocks still parse (unknown keys are stripped by zod's default "strip" mode, verified directly against zod v4), and both are pinned by tests. The migration is the minimum the spec allows (one nullable `derived jsonb` column, no grant regression since the table's revoke is table-wide rather than a per-column `REVOKE ALL`), `exposureCount` is a clean lift that keeps `costAt`'s own numbers unchanged, and the AC-15 task-side regression (the old code parsed against `snapshotBlocksV1Schema` by name, which zod would have silently stripped `derived` from) is fixed by a version-keyed lookup and is specifically pinned by two tests that fail if the lookup regresses to a hardcoded schema.

I independently re-derived the finding this branch's own review history already surfaced and withdrew — the cost line prefers the Suva rate before LTIFR while the derived block prefers LTIFR before Suva — and confirm it is a deliberate, written decision (`rationale.md:74`), not an oversight; AC-9 requires one shared *formula*, not one shared *input selection*, and the divergence is itself pinned by a test. I also re-verified the two items flagged for independent judgment: the unguarded `values.hours_per_fte` read is confirmed confined to `costAt`'s LTIFR arm alone (the derived block's own read of the same map is guarded), and the two comment-only hunks in `98cd29f` are factually accurate against the code they annotate. Typecheck, lint and the touched Vitest suites (166 tests across 13 files) pass locally at review time. One real gap: this diff extends a client component (`benchmark-section.tsx`) already carrying unfixed hydration failures from the project's documented ICU grouping hazard, without addressing or even flagging that reuse in the new work.

## Minor

### 🟡 New work lands inside a client component with known, unfixed hydration failures, `src/components/gallery/benchmark-section.tsx:56-97`
**Problem**: The project's own memory record states plainly that three pre-existing hydration errors "still fire on the `/admin/design` gallery's benchmark section as of 7 Sep 2026" and that "gallery one is unfixed" — caused by `format.number()` on a 4+ digit value inside a `"use client"` component (the pre-existing `chf(1_961_000)` etc. calls further down the same file, untouched by this diff). This diff adds a second block of new markup (the derived-counts section, lines 56-97) into that same already-broken client component, with nothing in the diff — commit messages, spec, or a code comment — acknowledging that the section it extends is a known-bad host. The new calls themselves (`format.number(0.9, "oneDecimal")`, `format.number(2.3, "oneDecimal")`) are single-digit and do not trigger the bug on their own, so this is not a new instance of the defect.
**Why it matters**: a reader hitting a hydration console error on `/admin/design` today has no way to tell, from this diff alone, that the derived-counts markup is innocent and the real cause is the untouched `chf()` calls lower in the same file. The natural next edit — wiring an inline exposure line (`format.number(derived.fte, "integer")`, already used in the real card) into this gallery section, which is literally an open follow-up on spec 0012 ("Decide whether the block should also state its exposure inline") — would land in a file where "is this number safe" cannot be answered by inspection, because the file already fails for an unrelated reason.
**Suggested fix**: a one-line comment at the top of `BenchmarkSection` (or a line added to the existing hazard note) flagging that this component is a known-affected host, so the eventual fix has an obvious place to start and a future edit here does not assume the file is clean.

## Strengths

- The version-safety restructure (`src/features/benchmark/snapshot.ts:168-171`) is exactly the mechanism the spec calls load-bearing, landed in its own commit (`24cb9cd`) ahead of the bump, and independently reverified here: `SNAPSHOT_SCHEMAS["benchmark-model@1"]` is `snapshotBlocksV1Schema`, unwidened, and `parseSnapshotBlocks` against a `@1` row whose raw payload carries a `derived` key still returns `blocks.derived === undefined` rather than an error, matching `SnapshotBlocks`'s optional `derived` type (`tests/features/benchmark/model.test.ts:596-605` pins this directly, and I confirmed the zod v4 "strip unknown keys" default behind it with a standalone script).
- `exposureCount(shape, rate, fte, hoursPerFte)` dispatches on the rate's **shape**, not on `costAt`'s narrower `incidentKpi` union — the detail that lets TRIFR share the formula honestly instead of widening a cost-model type that has no reason to know about it (`src/features/benchmark/model.ts:189-201`). `costAt`'s own numbers (`incidents`, `costPerCase`, `annual`) are unchanged by the lift, confirmed against the existing cost tests.
- AC-15's fix is pinned by mechanism, not just effect: `tests/trigger/benchmark-company.test.ts` has one test proving the write schema is looked up by `MODEL_VERSION` rather than named, and a second proving a version missing from the map throws instead of silently storing a partial block — the exact way the original bug would have failed.
- The `values` cast's runtime lie (`Record<AssumptionKey, number>` over a possibly-partial `Object.fromEntries`) is named in a comment at the point of the cast (`model.ts:295-299`). I confirmed the comment is accurate: the guard at `model.ts:439` is genuinely load-bearing, and the one place lacking the equivalent guard (`costAt`'s own read of `values.hours_per_fte` at `model.ts:212`, reached only on the LTIFR arm) is exactly what the comment points at and exactly what the scope's Deferred list (`docs/scope/index.md:74`) describes — confirmed by grep that `values.hours_per_fte` has no other call site anywhere in `src/`.
- Column grants: the table's write revoke (`revoke insert, update, delete, truncate on public.benchmark_snapshots from anon, authenticated`) is table-wide, not a column-level `REVOKE ALL` requiring a per-column re-grant, and there is no column-level `grant select (...)` pattern anywhere in this table's schema to regress — the AGENTS.md gotcha about grants dropped by the declarative diff genuinely does not apply to this migration, and the migration file needed nothing beyond the `ADD COLUMN` and the `COMMENT ON COLUMN` it already has.
- The pgTAP suite grew from `plan(20)` to `plan(23)` with exactly three new assertions (`has_column`, `col_is_null`, and a service-role insert of a `benchmark-model@2` row carrying a real derived block) — the plan count and the assertion count agree.
- Both message catalogs (`de-CH`, `en-CH`) gained the same eight `derived.*` keys with no drift between them.
