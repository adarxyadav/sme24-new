## Summary

This is a careful design refinement of the already-shipped marketing site (spec 0009) plus one genuinely new public surface: the SGAS expert register directory (1,929 entries) at `/expert-network/directory`, and a landing hero benchmark object (`HeroBenchmark`). The engineering is disciplined about the two traps this kind of feature usually falls into: the ICU-grouping hydration mismatch is explicitly guarded (deferred-until-mount rendering, plain-digit fallbacks) everywhere a large number touches a client component, and the register data is stripped of contact details at build time in the script rather than at render time, so the sensitive columns never enter the repo. The static contract (`(marketing)` stays free of `searchParams`/`headers()`/`cookies()`), the PATHNAMES/German-slug convention, `marketingMetadata`, `opengraph-image.tsx` and `JsonLd` are all present and correct for the new route, and it is wired into the sitemap and the bundle-budget gate honestly (same 250 kB ceiling as every other content page, not loosened). Message catalogs are in full parity (0 keys missing either side, whole file, not just the new namespace). Test coverage for the new directory surface is genuinely good (Vitest unit + component tests, a dedicated e2e spec proving prerendering and no-request filtering). The only real gaps are two accessibility findings on the results table (no accessible name/caption, and the live region only announces after the first mount rather than describing the table itself) and a couple of documentation nits.

## Minor

### 🟡 Results table has no accessible name, `src/features/marketing/ui/register-directory.tsx:150-183`
**Problem**: The `<Table>` rendering the register has no `aria-label`, `aria-labelledby`, or `<TableCaption>`. It sits under a section headed "register-heading" (`aria-labelledby="register-heading"` on the containing `<section>` in `directory/page.tsx:108`), so a sighted user can infer what the table is, but a screen reader user who navigates by table/landmark rather than reading linearly gets an unnamed table with no distinguishing text.
**Why it matters**: WCAG 2.2 AA's guidance on data tables (and Biome/axe's table-related checks, which only catch the more mechanical violations like missing `<th>`) expects a data table to have a discoverable purpose independent of surrounding prose. This is the one table on the page today, so the practical harm is low, but it's the kind of thing that regresses silently once a second table is added to the page.
**Suggested fix**: Add `aria-labelledby="register-heading"` to the `<Table>` (the id already exists on the section heading), or a visually-hidden `<TableCaption>` with the `marketing.directory.register.title` string.

### 🟡 Result count is silent until after mount, not just deferred, `src/features/marketing/ui/register-directory.tsx:142-144`
**Problem**: The `aria-live="polite"` paragraph renders `null` until `mounted` flips true (guarding the ICU grouping-character hydration mismatch, which is the right call), but that means a screen reader user who lands on the page and starts filtering before the first `useEffect` tick sees no "we're about to show you a count" cue — the paragraph goes from absent to present, which some AT/browser combinations announce inconsistently (a live region is usually expected to already exist in the DOM, with only its *content* changing, for the most reliable announcements).
**Why it matters**: Minor, given `useEffect` fires on the first tick and most users won't act faster than that, but it's a slightly fragile pattern for the one region whose job is to announce results after every filter change.
**Suggested fix**: Consider rendering the paragraph's markup immediately with an empty/`&nbsp;` placeholder and swapping only the text after mount, rather than swapping the whole node — keeps the live region stable across the mount boundary. Not blocking; the current approach is defensible and already better than the alternative (a hydration-mismatch crash).

## Strengths

- The hydration trap this review was specifically asked to hunt for is handled correctly and explicitly documented in-code: `register-directory.tsx:66-71` names the exact ICU apostrophe mismatch (`1'929` vs `1’929`), defers the only formatted-count render until after mount, and the canton `<option>` labels (`register-directory.tsx:110-115`) deliberately use plain digit interpolation instead of `format.number` with a comment explaining why. `HeroBenchmark` and `PackageCard`, the other two places flagged for scrutiny, are server components (no `"use client"`), so their `useFormatter().number()` calls are baked into the prerendered HTML once and carry no hydration risk at all — confirmed by reading both files.
- The bundle question got a real, honest answer rather than a rubber-stamp: `register.ts` is imported directly into the client component (not passed as a prop) specifically because a prop would double-ship the data through the RSC serialized payload as well as the markup — this reasoning is spelled out in both the component JSDoc and `docs/marketing.md`'s "Known limits" section, with real measured numbers (29.4 kB gzipped chunk, 31.1 kB of a 250 kB budget, 14 kB of headroom left) and a named next step (per-canton routes or `import()` on interaction) for when the register grows. `scripts/bundle-budget.mts` adds the new route at the same 250 kB ceiling as every other content page — the gate was extended, not loosened.
- Contact-detail stripping happens at the correct layer: `scripts/build-register.mts`'s `toEntry()` maps the 11-column `RawRow` (which carries address, phone, email, website) to the 8-column published `RegisterEntry`, which structurally cannot carry those fields — they're dropped before `register.json` is ever written, not filtered at render time. Backed by both a Vitest regex assertion (`register.test.ts`) and a component-level assertion (`register-directory.test.tsx`) and an e2e assertion, all checking the same invariant three different ways.
- The static contract is fully honored for the new route: no `searchParams`/`headers()`/`cookies()` anywhere under `(marketing)`, `PATHNAMES`/`MARKETING_ROUTES` carries the German slug (`/expertennetzwerk/verzeichnis`), `marketingMetadata("directory", ...)`, `opengraph-image.tsx` and a `CollectionPage` `JsonLd` block are all present, the route is picked up by `sitemap.ts` automatically (it enumerates `MARKETING_ROUTES`), and the e2e spec (`e2e/marketing.spec.ts:251`) proves the first 50 rows are in the prerendered HTML before any JS runs.
- Message catalogs are in complete parity — verified programmatically across the *entire* file (not just the new `marketing.directory` namespace): zero keys present in one language and missing in the other.
- New primitives (`HeroBenchmark`, `RegisterDirectory`, `SectionHeader` at all three tiers) are added to the ops-only `/admin/design` gallery via `marketing-section.tsx`, so axe scans them per the AGENTS.md rule.

## Test coverage

Test signal is `configured`; judged normally. The new directory surface is well covered:
- `tests/features/marketing/register.test.ts`: data-shape invariants on the real 1,929-row file (column count, known enum values, no contact detail via three different regexes, stable sort), plus unit tests for the pure `cantonCounts`/`capacityCounts`/`completedIn`/`filterRegister` functions on hand-written fixture rows.
- `tests/features/marketing/register-directory.test.tsx`: component-level behavior — first-page row count, the "N of total" count text, canton/capacity filter narrowing, name/town search, empty state and clear, "show more" pagination, and a repeat of the no-contact-detail guarantee at the DOM level.
- `e2e/marketing.spec.ts`: the directory page is in the same axe/theme/locale matrix as every other marketing page (both themes × both locales), plus two dedicated specs proving (a) filtering is a zero-network client operation with the prerendered rows already in the HTML, respecting the hydration-timing gotcha by waiting for the mount signal before interacting, and (b) the expert-network page links into the directory in both languages.
- `scripts/build-register.mts`'s pure functions (`cantonOfPostcode`, `postcodeOf`, `townOf`, `capacityOf`, `statusOf`, `toEntry`, `toRegister`) are not directly unit tested in this diff, but every one of their outputs is exercised transitively through the committed `register.json` and the invariant tests above (column shape, no contact detail, stable sort). Given the script is hand-run and its output is the artifact under test, this is a reasonable place to stop — a Minor at most, not raised as a blocking gap.

The conclusion from the 8 Sep `/test` run (no new tests needed beyond what's in the diff) holds for everything except the brand-new register directory surface, which in fact got a full, purpose-built suite across all three layers (unit, component, e2e) — stronger than "no new tests needed" suggests, if anything.
