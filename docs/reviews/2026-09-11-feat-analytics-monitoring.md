# Review, feat/analytics-monitoring, 2026-09-11

**Reviewed by**: sonnet (author on opus)
**Scope**: 40 files, branch vs main (merge base `212dd39`)
**Verdict**: Changes requested

## Summary

Spec 0017 lands a typed analytics catalogue (`ANALYTICS_EVENTS` plus a per-event Zod schema under a `satisfies` check), retypes `captureServerEvent`/`captureBrowserEvent` to accept only catalogue names, wires nine server-side funnel events and one consent-gated browser event, adds a `task.failed` ops alert from the existing `onFailure` hook, and wires a Sentry release/source-map pipeline. The catalogue, the capture functions, and the consent-independence story are all well built and well tested — `tests/lib/analytics/server.test.ts` and `consent-independence.test.ts` in particular are excellent, mutation-checked guards against real regressions. The one real defect is in `src/trigger/benchmark-company.ts`: unlike `research-company.ts` and `confirm-order.ts`, it has no guard against firing `benchmark.computed` twice for one logical computation when a retried attempt reinserts a snapshot row, which is exactly the invariant AC-8 and the runbook state as required. A second, narrower issue is systematic under-testing at the six new server-action/task call sites, where `captureServerEvent` is stub-mocked to avoid the `server-only` import crash but the event name and properties actually sent are never asserted.

## Major

### 🟠 `benchmark.computed` can double-fire on a retried attempt, `src/trigger/benchmark-company.ts:147-191` — **fixed**

**Resolution (2026-09-11)**: `captureServerEvent` gained an optional `dedupeKey`, mapped to PostHog's
event `uuid` (its own deduplication handle) through a deterministic SHA-256 digest shaped into the
version 5 form. `benchmark-company` passes `benchmark-computed/<ctx.run.id>`: one id for every
attempt of one logical run, a different id for every legitimate recompute, so the retry collapses
and the recompute still fires. Keying off the run id rather than off `hadSnapshot` or a read-back of
the inserted row is what keeps both halves true. The `:550` retry test now asserts the capture count
and the full event, and was mutation-checked — removing the `dedupeKey` line fails it.

**Problem**: `hasSnapshot` (line 147) is read only to decide whether to resend the "first snapshot" email (`first`/`send`, lines 175-183); it is not a guard on the insert itself. Every task attempt performs an unconditional `insert` into `benchmark_snapshots` (lines 148-174), by design — snapshots are immutable and append-only (spec 0008/0012), and the file's own comment at line 146 and the test at `tests/trigger/benchmark-company.test.ts:550` ("sends the email the crashed attempt owed when a retry inserts a second row") document and test that a crashed attempt leaves a snapshot row behind and a retry inserts a **second** row. `captureBenchmarkComputed` (line 191) runs unconditionally after every successful insert, with no check against `hadSnapshot`, no idempotency key, and no read-back of "did an earlier attempt already emit this." If attempt 1 completes its insert and even reaches `captureBenchmarkComputed`, but the process is killed or times out before Trigger.dev records the run as succeeded (well within the `maxDuration: 120` / `retry: { maxAttempts: 3 }` budget on this task), attempt 2 reruns the whole body, inserts a second snapshot row, and fires `benchmark.computed` a second time for the same logical computation. This is the exact scenario `docs/analytics.md:42` calls out as the rule to protect ("a retried attempt that crashed mid run must not emit a second event for one logical run") and the exact scenario AC-8 states explicitly for this task by name ("`benchmark-company` retries up to three times, so `benchmark.computed` fires after the snapshot insert"). Contrast with `research-company.ts:231-243`, which guards its terminal write with `patchRun(..., "running")` and checks `finished === 0` before ever calling `captureResearchFinished`, and with `confirm-order.ts:141`, which checks `settled.data.alreadySettled` before calling `capturePaymentCompleted`. `benchmark-company.ts` has no equivalent guard.

**Why it matters**: The funnel step `benchmark.computed` — one of the five steps in the Release-1 funnel insight (`docs/analytics.md:52-57`) — would silently overcount for any company whose computation retried after a partial success, undermining exactly the "readable funnel" goal the whole spec exists to deliver, and doing so invisibly: a duplicate event looks identical to two real computations.

**Suggested fix**: Guard `captureBenchmarkComputed` the same way the other two call sites are guarded — either only fire it when `hadSnapshot` was false at read time (mirroring `first`, though that changes the semantics for legitimate recomputes) is wrong since recomputes are meant to refire; the correct fix is closer to `research-company.ts`'s pattern: derive "did *this* attempt's insert win" from the inserted row itself (e.g. compare `inserted.created_at` against a re-read of the most recent row's timestamp before firing, or thread the crashed attempt's own snapshot id through so a retry that finds a prior insert from the same run skips the capture). At minimum, key the capture off something that survives a retry, the same way `sendBenchmarkReady` survives one via `benchmark-ready/<companyId>/<userId>`.

## Minor

### 🟡 New `captureServerEvent` call sites are mocked but never asserted, six files

**Problem**: Every new `captureServerEvent` call site added by this diff — `requestResearch` (`lookup.started`, `src/features/research/actions.ts:114-127`), `saveClientKpis` (`kpi.client_saved`, `src/features/self-assessment/actions.ts:187-199`), `clearClientKpi` (`kpi.client_cleared`, `src/features/self-assessment/actions.ts:245-256`), `startCheckout` (`checkout.started`, `src/features/checkout/actions.ts:300-312`), `captureResearchFinished` (`research.finished`, `src/trigger/research-company.ts:253-258`), and `captureBenchmarkComputed` (`benchmark.computed`, `src/trigger/benchmark-company.ts:191`) — has its test file add only `vi.mock("@/lib/analytics/server", () => ({ captureServerEvent: vi.fn().mockResolvedValue(true) }))` (e.g. `tests/features/research/actions.test.ts:46`, `tests/features/self-assessment/actions.test.ts:66`, `tests/trigger/research-company.test.ts:72`, `tests/trigger/benchmark-company.test.ts:49`) to stop the `server-only` import from crashing the suite under test. None of these six sites has an assertion on the event name or the properties passed — no `toHaveBeenCalledWith`. Only `enquiry.sent` (`tests/features/marketing/actions.test.ts:287-293`, pre-existing, just renamed) and `payment.completed` (exercised only indirectly by whichever `confirm-order` test suite covers the full task run, not spot-checked here) get any assertion at all. `tests/lib/analytics/consent-independence.test.ts` exercises literal example payloads built by hand, not the real call sites, so it cannot catch a wrong id passed at a call site (e.g. `organizationId` and `companyId` transposed, or the wrong row's `created_by` used as `distinctId`) — exactly the failure mode the catalogue's own property schemas exist to catch structurally, but that a schema which merely requires "a uuid" cannot catch semantically.

**Why it matters**: This is new logic wiring real domain values (ids, counts, locales) into event properties at six call sites, none of it covered by a behavioral test. A transposed `organizationId`/`companyId` pair, a `distinctId` sourced from the wrong row, or a `kpiKeysSent` off-by-one would type-check, pass every existing test, and silently corrupt the funnel data — the guide's bar for "branching logic, error handling, or security-relevant" new logic at Major severity almost applies; it is scored Minor here because the catalogue's Zod schemas do catch shape errors (wrong type, missing field), just not semantic ones (right shape, wrong value).

**Suggested fix**: At each of the six sites, add one assertion checking `captureServerEvent` (or the task's mocked version) was called with the expected event name and the specific property values sourced from the test's own fixture data, the way `tests/features/marketing/actions.test.ts:287-293` already does for `enquiry.sent`.

## Nits

- ⚪ `src/lib/analytics/server.ts:56-67`, confirmed deliberate per the verify record: a new `PostHog` client is constructed and `shutdown()`ed per call. Worth revisiting only if the nine-event-per-funnel-run cost becomes measurable; not a defect as built.
- ⚪ `src/features/benchmark/ui/benchmark-viewed.tsx:35-46`, confirmed deliberate: the `useRef` guard is what actually prevents a refire; the effect's dependency array (all four ids) is inert for that purpose since the ids never change across the component's mount. Reads oddly but causes no bug — a `// eslint-disable`-style dependency comment would make the intent clearer to the next reader.
- ⚪ `src/lib/alerts/schema.ts:100`, `attempts: z.number().int().positive()` — Trigger.dev attempt numbers start at 1, so this is correct as written, not a bug; flagging only because a reader unfamiliar with the SDK's numbering might wonder if `0` should be valid.

## Strengths

- `tests/lib/analytics/server.test.ts` and `tests/lib/analytics/consent-independence.test.ts` are excellent: the consent-independence suite's structural guard (asserting `server.ts` and `catalogue.ts` never import the consent module, `CONSENT_COOKIE`, or `next/headers`) is exactly the right kind of test — it fails the moment someone "fixes" the funnel by threading a consent check into the server path, which is the actual risk, not a transport bug. The verify record notes it was mutation-checked.
- `research-company.ts` and `confirm-order.ts` get the retry-safety question genuinely right: `finished === 0` and `alreadySettled` are correct, minimal guards against the exact double-fire risk that `benchmark-company.ts` misses, which makes the omission in the latter easy to miss on a first read since two of three task call sites model the right pattern.
- The catalogue's `as const satisfies Record<AnalyticsEvent, z.ZodType>` plus `tests/lib/analytics/catalogue.test.ts`'s runtime mirror of that check (every name has a schema, every schema requires `locale`, every event is in exactly one of the two organization groups) is a genuinely strong defence against the exact vocabulary drift the spec exists to fix.
- `docs/legal/record-of-processing.md` and `docs/analytics.md` both state the two-basis story (`interest` for the nine server events, `consent` for `benchmark.viewed`) precisely and consistently with what the code does — checked against the running app in the verify pass, not just the prose.
- The `enquiry.sent`/`expert.profile_completed` renames (AC-7) are clean: the old `ENQUIRY_SENT_EVENT` constant and the old `expert_onboarded` string are both fully gone, confirmed by grep in the verify record.

## Test coverage

Strong at the unit level for the shared infrastructure (`catalogue.ts`, `server.ts`, `client.tsx`) and for the consent-independence claim, which is the correct place to put the heaviest test weight since a regression there is silent and load-bearing. Weak at the individual call-site level: six of nine server-side capture calls are exercised only enough to avoid a test-environment import crash, with no assertion on what is actually sent — see the Minor above. The one genuine correctness gap (the `benchmark-company.ts` double-fire risk) is not caught by any test either; `tests/trigger/benchmark-company.test.ts:550`'s "sends the email the crashed attempt owed" test proves the team already knows attempts leave duplicate snapshot rows behind, but stops short of asserting anything about the capture call count in that same scenario, which is precisely where the bug would have shown up.
