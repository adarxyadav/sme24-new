## Summary

Spec 0016 changes what the benchmark claims rather than its arithmetic: peer rows now declare a derived `shape` (`point` vs `distribution`), two new position bands replace quartile wording where no real spread exists, the CHF headline leads with a range, assumptions and peer rows carry an honesty caveat through to the disclosure, and the launch gate splits `provisional` from `is_assumption`. The database migrations are correctly split (schema, then seed) and the generated seed migration matches the CSV exactly. The model, snapshot versioning (`@3`, additive over `@1`/`@2`), UI point-row rendering, and the marketing-example drift test are all well built and thoroughly tested at every layer (pgTAP, Vitest, Playwright+axe). The one real gap is that the new `basis`/`source_key` columns and the `benchmarks_basis_check` constraint — explicitly called out in the spec's own test-scenario list — have no pgTAP coverage, unlike the pre-existing `source_note` check they mirror. A second, minor issue: the `positions.peerStatus.pendingTitle` message key is defined in both catalogs but never rendered, leaving AC-8's "pending" wording thinner than intended.

## Minor
### 🟡 `basis` shape check and `source_key` column have no pgTAP coverage, `supabase/tests/benchmarks.test.sql`
**Problem**: The migration adds `source_key text null` and `basis jsonb null` with a `benchmarks_basis_check` CHECK constraint mirroring `source_note`'s (both-or-neither `de`/`en` keys). `supabase/tests/benchmarks.test.sql` tests the `source_note` shape check (line 118-120: "a source note without both locales is rejected") but has no equivalent assertion for `basis`, and no test that `source_key` accepts free text or null. The spec's own critical-test-scenarios list (index.md) explicitly names this: "pgTAP proves the five new columns exist with their null and default rules and the localized `basis` shape check."
**Why it matters**: The CHECK constraint is otherwise unverified by the pgTAP suite that is supposed to be the safety net for schema changes; a future edit to the constraint (or an accidental removal during a later migration) would not be caught by `pnpm test:db`. Vitest covers the CSV-level `basis_de`/`basis_en` both-or-neither rule (`seed-schema.ts`'s refinement), but that only proves the CSV parser rejects a half pair before generating SQL — it says nothing about whether the database itself enforces the same rule on a row inserted outside the seed path (e.g., a future ops UI or a hand-written migration).
**Suggested fix**: Add a `throws_ok` case for `basis` with only one locale key (same pattern as the existing `source_note` case at line 118-120), and a `lives_ok`/`is` case that `source_key` and `basis` accept null and a valid `{de, en}` value.

### 🟡 `positions.peerStatus.pendingTitle` is dead: a `pending` KPI never renders a distinct title, `src/features/benchmark/ui/benchmark-segment.tsx:720-732`
**Problem**: Both message catalogs define `benchmark.positions.peerStatus.pendingTitle` ("No peer data yet" / "Noch keine Vergleichsdaten"), and the existing test suite (`tests/features/benchmark/ui/benchmark-segment.test.tsx:520,533`) only asserts that a `pending` KPI's row does **not** show `noSourceTitle`, never that it **does** show `pendingTitle`. Grepping the whole `src/` tree confirms `pendingTitle` is referenced nowhere in application code — only the generic, pre-existing `t("positions.noPeer")` title renders for a `pending` KPI, with `peerNote` appended below it.
**Why it matters**: AC-8 asks for "a 'not yet' wording that names what is awaited" for pending KPIs, distinct from the sourceless wording. The current behavior technically satisfies this (the `peerNote` sentence does name what is awaited), but the dedicated `pendingTitle` string was written and translated in both languages specifically for this purpose and is unreachable dead content, which will confuse whoever next touches this catalogue entry into thinking it's already wired up.
**Suggested fix**: Either render `pendingTitle` as the title span for a `pending` KPI (paralleling the `noSourceTitle` branch) or remove the unused key from both catalogs and note in `docs/benchmark.md`/the spec's KPI status table that `noPeer` is the deliberate pending title.

## Strengths
- The two-migration ordering (schema DDL first, seed upsert second, later timestamp) is followed exactly as AC-1 demands, and the generated seed migration was diffed and verified to match the committed CSV row-for-row.
- `tests/features/marketing/benchmark-example.test.ts` (AC-14) computes the landing-page franc figure from the real model over the actual committed CSVs rather than a fixture, so a seed edit that silently changes the marketing claim now fails the build — exactly the guarantee the spec asks for.
- `tests/features/benchmark/runbook.test.ts` (AC-17) parses `docs/benchmark.md`'s own "Expected, and only these" sentence and cross-checks it against the CSV's declared assumption keys by set equality, closing a drift class (a curator clearing a flag without updating the runbook) that would otherwise go unnoticed.
- The point-row Playwright test (`e2e/benchmark.spec.ts`) drives a real snapshot through the product's own save-and-recompute path (not a rendering fixture) and asserts the forbidden words ("quarter", "quartile", "median", "p25", "p75") are absent from the rendered row text, plus a dedicated axe pass.
- `SnapshotBlocks`/`SNAPSHOT_SCHEMAS` correctly keep `@1` and `@2` schemas literal and unrenamed while adding `@3`, and a dedicated test (`model.test.ts`) proves a stripped v2-shaped row still parses under `@2` but is rejected under `@3`, directly exercising the backward-compatibility invariant spec 0012/0016 require.
