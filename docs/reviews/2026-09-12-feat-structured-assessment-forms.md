# Review, feat/structured-assessment-forms, 2026-09-12

**Reviewed by**: Claude Sonnet 5 (author on Claude Opus 5)

**Verdict**: Approve with nits

## Summary

Spec 0019 turns Phillip's two EHS checklists (ISO 45001, 18 technical standards / 327 items) into versioned database content and builds one questionnaire engine — autosaving ratings and notes, suggesting annex clause ratings, letting Compliance standards be excluded, and locking the assessment on submit with one pure scoring function. This is a large, database-guard-heavy feature (two new schema files' worth of kind G content tables plus two kind T tenant tables, two triggers, an autosave queue with retry/backoff, an AI-assisted German translation pipeline, and a 708-line e2e spec), and it is executed with unusual precision against its own spec: every one of the "four things `db:diff` misses" is correctly hand-fixed, RLS matches the security-model table cell for cell, the autosave contract (coalescing, latest-value-wins, debounce, backoff, lock-freeze) is implemented exactly as specified and is proven with fake-timer tests rather than asserted by inspection, and the AC-10 "no client ever sees an answer" guarantee is structurally enforced (both surfaces share one narrow `AssessmentState` type that cannot carry a score or note) and independently proven by both pgTAP and a real e2e PostgREST probe. No blockers or majors were found across the database layer, the actions/queries/model layer, the UI/autosave layer, the content-build/translation pipeline, or the e2e/docs layer. The issues that do exist are all Minor or Nit: a couple of low-risk fragility points (a positional e2e locator, an unmounted-component save race that React 19 already no-ops safely), a schema-boundary looseness in one analytics field, and a documentation-precision gap between AC-1's prose ("within a section") and the code's correct actual behavior ("within a group" for Compliance).

## Minor

### 🟡 `assessment.started`/`assessment.submitted` analytics schema does not enum-constrain `questionnaireKey`, `src/lib/analytics/catalogue.ts`
**Problem**: The Zod schema for these two events types `questionnaireKey` as `z.string().min(1).max(50)` rather than `z.enum(QUESTIONNAIRE_KEYS)`, unlike the tighter typing used elsewhere in the same schema and unlike `RATING_CODES`'s enum treatment elsewhere in this feature.
**Why it matters**: AGENTS.md's analytics rule is built on the premise that a bad payload is refused by the schema, not merely by the call site's static type. A future call site (or a refactor that widens the `QuestionnaireKey` type before the catalogue's enum is updated) could pass a stray string through undetected by the schema itself, and PostHog would silently accept it. Low risk today since the only call sites are the two actions in `actions.ts`, both correctly typed.
**Suggested fix**: Tighten `questionnaireKey` to `z.enum(QUESTIONNAIRE_KEYS)` in `analyticsProperties`, matching the rigor already used for `RATING_CODES`.

### 🟡 Prompt version is never persisted alongside translated content, `src/features/assessments/translate.ts`, `scripts/build-questionnaires.mts:179`
**Problem**: `PROMPT_VERSION = "questionnaire-translation@1"` (`src/lib/ai/prompts/questionnaire-translation.ts:8`) is logged to the console during a build run but never written into the content file's metadata (no field on `ContentFile`, nothing in `sourceNote`).
**Why it matters**: If a reviewer later asks "which prompt version drafted this German text," the committed JSON gives no answer — only `git blame` on the prompt file does, and that doesn't tell you which build run actually used it. Given the reuse rule keys strictly on unchanged English text, a prompt-only change (e.g. a glossary correction) does not force a re-draft, which may be intended, but it is undocumented as a deliberate tradeoff.
**Suggested fix**: Either add a small metadata field (`translatedWithPromptVersion`) to items drafted by the AI Gateway, or add one sentence to `docs/assessments.md`'s German review loop section stating that a prompt version bump alone does not invalidate cached German text.

### 🟡 Label-restoration scope reads "per section" in AC-1 prose but is implemented "per group" for Compliance, `src/features/assessments/content-build.ts:148, 206-207`
**Problem**: AC-1 says "a label repeated within a section gets a trailing 0 on its later occurrence." For ISO 45001 (no groups) `restoreLabels` is scoped per section, matching the prose. For Compliance, it is scoped per **group** (called once per `group.clauses`), because two different groups within the same section legitimately reuse `1.1`, `1.2`, etc. — grouping by section instead would wrongly collide them.
**Why it matters**: The implemented behavior is correct (confirmed by `content.test.ts`'s "no label repeats within a group" assertion and the exact-count/exact-fix tests), but the mismatch between the AC's literal wording and the code's true invariant is exactly the kind of thing a future maintainer "fixes" back to the wrong (section-scoped) behavior while trying to honor the spec text, silently breaking the ten affected standards again.
**Suggested fix**: Add a one-line comment at `content-build.ts:206` (or a `rationale.md` note) stating explicitly that the restoration is scoped per-group for Compliance and why, so a future reader doesn't "correct" it against AC-1's literal wording.

### 🟡 `startAssessment`'s "newest matching booking" path has no test for two simultaneously-open matching bookings, `src/features/assessments/actions.ts:149-154`
**Problem**: `bookings.find(...)` picks the first match from `listExpertBookings`'s `scheduled_at desc` ordering, which is correct per spec ("the caller's newest booking"), but no test constructs two bookings for the same company/questionnaire that are both open (`scheduled`/`in_progress`) to confirm the later-`scheduled_at` one wins, including the edge of a `scheduled_at: null` booking sorting last.
**Suggested fix**: Add one test case with two matching open bookings to lock in the tie-breaking behavior explicitly, since a re-scheduled visit is a realistic real-world case for this pilot.

### 🟡 `purgeAuditRows`'s cleanup SQL is built by string interpolation rather than parameter binding, `e2e/db.ts:260-299`
**Problem**: The `DELETE ... WHERE id IN (${list(...)})` statements interpolate validated (UUID-regex, `^[a-z_]+$`-regex) strings rather than binding parameters, then shell out via `execFileSync("psql", [...])`.
**Why it matters**: Not exploitable today — every call site passes hardcoded table names and ids sourced from the service-role client's own inserts, and the regex guards close the obvious injection vector — but it is a SQL-injection-shaped pattern in test-only tooling that a future call site with a less-trusted input could reopen.
**Suggested fix**: Prefer `psql -v` variable substitution or a real Postgres client with parameter binding, for hygiene rather than an active vulnerability.

### 🟡 Positional e2e locator for the clause's own rating control, `e2e/assessments.spec.ts:132-138`
**Problem**: `ratingRadio` finds the clause's own rating group via `.last()` under a `[data-item]` selector, relying on DOM nesting order (annex sub-items render above the clause's own fields), documented in a comment but not defended by a data attribute.
**Why it matters**: A future layout change (e.g., moving the Apply-suggestion row) would silently break this locator's assumption without a test failure that points at the real cause.
**Suggested fix**: Add an explicit `data-owner="<item-id>"` (or similar) to the clause's own rating control and match on that instead of position.

### 🟡 `section-items.tsx`'s async save has no unmounted-guard for in-flight promises, `src/features/assessments/ui/section-items.tsx:156-214, 275-287`
**Problem**: Switching sections remounts `SectionItems` (`key={openKey}`); the unmount cleanup only flushes pending debounce timers, not a save already in flight. When that promise resolves post-unmount, `patch()` calls `setState` on the old instance's setter.
**Why it matters**: React 19 no-ops this safely (no crash, no stale UI, since the new instance never reads the old setter), so this is not user-visible, but it is a wasted render and would warn under stricter React versions or testing modes.
**Suggested fix**: Track in-flight sends with a mounted-ref or `AbortController` and skip the `setState` after unmount, for hygiene rather than a live bug.

## Nits

- ⚪ `src/features/assessments/queries.ts:243`, `listAssessments` filters items into an assessment's version by `item.id.startsWith(\`${row.questionnaire_version_key}/\`)` — a string-prefix match on a composite id rather than a structured field comparison; safe today given the regex-enforced `version_key` shape, but fragile to a future id-format change.
- ⚪ `src/features/assessments/model.ts:265-276`, `gapList` spreads `[...items]` before `.filter()`, which already returns a fresh array — the spread is redundant, negligible cost.
- ⚪ `supabase/schemas/62_assessments.sql`, the `expert_bookings` view's deviation comment describes the generic "`select *` gets rewritten" `db:diff` gotcha, but in this migration only the grant needed hand-fixing — the column list was never `select *` to begin with. Comment is accurate in spirit, slightly overstates what happened in this specific migration.
- ⚪ `supabase/schemas/61_questionnaire_items.sql`, the self-referencing `parent_id` FK is not `deferrable initially deferred`, so parent-before-child insert ordering in `seed-migration.ts` is load-bearing, not just a defensive nicety — worth a short comment next to the FK declaration noting this, since a future refactor of the renderer's batching could reorder statements and break it.
- ⚪ The review brief's file list names `tests/features/gallery/assessments-section.test.tsx`; the actual (adequate) file lives at `tests/components/gallery/assessments-section.test.tsx`, mirroring its source path — no functional issue, just a path correction for the record.
- ⚪ `src/features/assessments/ui/section-nav.tsx:62-77`, an excluded section's nav entry drops its historic rated count entirely rather than showing it alongside the excluded badge — matches spec intent ("shows... as excluded"), not a defect.

## Strengths

- The autosave queue (`section-items.tsx`) implements the full described contract exactly — one in-flight save per item, coalescing with latest-value-wins, immediate rating saves, 800ms/blur note debounce, three retries at 1s/2s/4s backoff, `beforeunload` while pending/failed, and a `locked` result freezing the page — and the test suite proves it with fake timers exercising the exact debounce and backoff boundaries, not just the happy path.
- Every one of AGENTS.md's "four things `db:diff` misses" was correctly identified and hand-fixed in the migrations: the `assessments` column grant (`status, site, conducted_on` only), and the `expert_bookings` view's grant narrowing to `SELECT` for `authenticated`. No spurious `public` function needed the anon-execute revoke, and the view was never rewritten to `select *`, so those two gotchas correctly did not require intervention.
- RLS and the two triggers (`check_assessment_transition`, `check_assessment_open`) match the spec's security-model table and state-transition semantics exactly, including the least-obvious cell: the lock trigger blocks every role, including the service role, on a submitted assessment's answers — and this is proven live in pgTAP, not just asserted.
- The AC-10 "no client ever sees an answer" guarantee is structurally, not just conventionally, enforced: both the client card and the ops orders table render the same narrow `AssessmentState` type (`states.ts`), which has no field for a score, rating, or note, so a future page cannot leak one without changing a shared type everyone would notice. This is independently proven twice — pgTAP for the database boundary, and a real e2e PostgREST probe (reassembling the client's own access token to query `assessment_answers` directly and assert zero rows via both a body check and a `Content-Range: count=exact` header) for the API boundary.
- The read-then-write pattern used to distinguish `not_found` from `locked`, and the insert-then-fallback-to-update pattern used to upsert onto a partial unique index (PostgREST can't upsert those directly), are both non-obvious, correctly reasoned solutions, applied symmetrically across `saveAnswer` and `setSectionExclusion`, and both are directly tested for their race conditions (a concurrent insert/update losing the race falls through correctly).
- The fire-and-forget rule for analytics and the ops alert is not just followed but proven: `actions.test.ts` includes an explicit test that `submitAssessment` still answers `ok` when the alert send throws, directly validating the single most load-bearing cross-cutting rule this codebase has for this pattern.
- `classifyAssessmentError` maps every Postgres fragment and error code the two triggers can raise to a typed result, with an unrecognized fragment safely falling through to `unexpected` (and Sentry) rather than guessing — avoiding a wrong classification of a future, unanticipated trigger message.
- The content pipeline's `ContentFixError` (thrown when an override's target text is no longer present, e.g. because the upstream export changed) is a genuinely good "stale rule" detector for a whole class of content-pipeline bug that normally fails silently.
- The migration renderer's test suite diffs its fresh output against the actual committed SQL file (not just a fixture), so the JSON content and the SQL that seeds it can never silently drift — a stronger guarantee than most generator-verification setups provide.
- Accessibility is comprehensively correct: the rating control is a genuine Radix radio group with tested arrow-key navigation and a non-color-only selected state; the save indicator is `aria-live="polite"`; the section nav is a real `<nav><ol><li><Link>` list; axe runs on both new pages in both languages including the submitted/locked state; keyboard operation of the rating control is tested with real key events, not synthetic clicks; and the font-weight ceiling (≤600) holds throughout, spot-checked in both the UI review and the e2e spec itself.
- No instance of the useEffect-watching-useActionState anti-pattern was found anywhere in the diff — every `useFormAction` consumer and the hand-rolled autosave queue alike do their success work (toast, `router.refresh`, navigation) inside the awaited handler, exactly as AGENTS.md requires.

No untested new logic of any real consequence was found; the two gaps noted above (multiple simultaneous open bookings; the positional e2e locator's fragility) are coverage-quality nits, not missing-coverage blockers.
