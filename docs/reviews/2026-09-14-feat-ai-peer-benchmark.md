## Summary

This is a clean, disciplined rewrite: the curated peer library and Swiss-only cost model are replaced end to end by a research-driven peer search (`research-peers` task), a pure loss formula (`loss.ts`), and a rewritten `benchmark-model@7`. I independently recomputed both worked examples from the spec (the CHF 365,715 client loss and the ~15x BASF/Rieter peer-loss ratio) and both match the code exactly. The task boundary that keeps a peer-search failure from ever touching `research_runs.status` or raising an ops alert is enforced by the type system, not just convention (`patchRun`'s update type structurally excludes `status`/`error_code`). RLS on `research_peers` is thorough — tenant isolation, expert/ops access, anon rejection at the grant level, write-verb revocation, and the run cascade are all pgTAP-tested. All four of the declarative-diff's known blind spots are hand-fixed in the migrations and explained in comments. The three issues verify already flagged are confirmed to exist, and one (the orphaned test) is materially worse than verify characterized it: the surviving assertion doesn't just test dead prose, it tests a claim ("no longer says peer values are provisional") about copy nothing in `src/` renders, so the assertion is meaningless rather than merely redundant.

## Majors

### 🟠 The surviving catalogue.test.ts assertion checks a property of unrendered copy, not a live claim, `tests/features/benchmark/catalogue.test.ts:101-113`
**Problem**: The whole `benchmark.positions` namespace (including `provisionalNote`) is dead: nothing in `src/` reads it after the peer-standing component was deleted (confirmed by the same grep the prior verify report ran; I re-confirmed no reader exists). `tests/features/benchmark/catalogue.test.ts:101-113` still runs two `it` blocks against this namespace — one asserting the description names no quartiles/disclosure, one asserting `provisionalNote` "no longer claims peer values are provisional." AC-4 says `peerStatus` and `peerNote` should leave "the catalogue and the catalogs"; they left the catalogue only, so this test's premise (that this copy still means something) is false on both counts.
**Why it matters**: This is worse than the "20 orphaned keys" framing suggests. A dead message key sitting unused is inert; a passing test that asserts semantic properties ("this text no longer implies X") about a string nothing displays is actively misleading — a future reader sees green here and reasonably assumes the positions block still ships. It also means a `/sync` pass or future contributor might be blocked from deleting the namespace by a test that looks meaningful but tests nothing real.
**Suggested fix**: Either delete the two `it` blocks (and the `benchmark.positions` messages) now as part of finishing AC-4 properly, or, if that's deliberately deferred to `/sync`/`/test`, add a one-line comment above the describe block noting the namespace is dead and the test is scaffolding until removal — so the next reader doesn't mistake it for coverage of live behavior.

## Answers to the specific questions

**a. The money formula and constants (`loss.ts`)** — Fine. Arithmetic is correct: I independently recomputed both the spec's client example (LTIFR 6, TRIFR 10, 500 FTE → 365,715.00) and the peer example (BASF vs. Rieter → ratio 15.29, matching the spec's "about fifteen times") in Python from the formula as coded, and both matched to the cent. Units are consistent: `HOURS_PER_FTE` (1800) is the single denominator every rate is quoted against, and the unit conversion into "per million hours" happens once, upstream, in `peer-schema.ts`/`resolve-peers.ts` — `loss.ts` never sees a raw published unit. The "5x trap" is handled correctly (`per_200k_hours` and `per_100_workers` both ×5, consistent since 5×200,000=1,000,000 and 100 workers × 2000 hours ≈ 200,000 hours). Constants are documented with one-line JSDoc citing which AC they serve and noting the two (`HOURLY_COST`, `FATALITY_COST`) that must never render. Zero/missing/extreme inputs are handled: the loss block is explicitly null without a positive `fte` or without an LTIFR (`model.ts:277`); a TRIFR below LTIFR contributes zero rather than a negative recordable term (`Math.max(0, trifr - ltifr)`); a peer without a headcount gets a null `estimatedLoss` rather than a fabricated one. No path I found produces a nonsense CHF figure from a legal input.

**b. The rung ladder (`resolve-peers.ts`)** — Fine, and total. `climbRung` (lines 161-173) always returns: an empty peer list returns `{rung: null, peers: [], thin: true}` immediately rather than falling through; otherwise it checks country (≥3 → return), then region (≥3 → return), then falls through to `world` unconditionally, computing `thin` from the count. There is no loop and no path that returns without a rung when peers.length > 0. The one edge case I checked closely — zero *kept* peers after the self/unsupported drops — produces `peers: null` in `peersBlockOf` (`model.ts:161`, `rows.length === 0` guard), and `benchmarkStateOf` (`queries.ts:127-136`) reads a snapshot with both `loss` and `peers` null as `noData`, not `ready`. So the UI cannot render an empty peer set as if it were a real comparison — it falls to the explicit no-data state. I did not find a way to make the ladder loop or silently drop to an empty "real" table.

**c. Can `research-peers.ts` ever write `research_runs.status` or raise an ops alert?** — No, confirmed by both static typing and full-file review. `patchRun`'s parameter type (`research-peers.ts:311-317`) is `Pick<..., "peer_provider_run_id" | "summary">` — `status` and `error_code` are structurally excluded, so any attempt to pass them would be a compile error, not just a convention. Every write call in the file (`patchRun`, `writePeersSummary`) goes through this narrowed type. A grep of the file and everything it imports (`resolve-peers.ts`, `validate-peers.ts`, `peer-schema.ts`, `provider.ts`, `parallel.ts`, `fixture.ts`) for `raiseAlertFromTask` or any `ops-alert` import returns nothing; the only alerting is `Sentry.captureException` (both in the happy path's `triggerBenchmark` catch and in `onFailure`), which is the AC-7-sanctioned "one `log.warn` line" channel plus internal error tracking, not the product's ops-alert system (contrast with `benchmark-company.ts`, which does call `raiseAlertFromTask({kind: "benchmark.failed", ...})` in its own `onFailure` — a different task, deliberately not this one).

**d. RLS on `research_peers` and its migration** — Fine, and it does hand-fix all four diff blind spots. Tenant boundary: `supabase/tests/research_peers.test.sql` proves isolation (a member of org A sees only org A's 2 rows, not org B's; org B's member sees only their 1; an assigned expert sees the organization's rows; ops sees all 3; anon is rejected at the grant with `42501` rather than filtered to zero by RLS; every write verb fails with `42501` for a member and even the service role cannot truncate; the run-delete cascade removes its peer rows). App-role grants: SELECT-only for `authenticated`, everything else revoked in the schema file and independently in the migration. All four things the declarative diff is known to miss are present by hand in `20260913230341_spec_0022_peers_experts.sql`: (1) the `anon` column-grant revoke after the table-level REVOKE (`REVOKE ALL ... FROM anon`, line 290, plus the standard `MAINTAIN, REFERENCES, SELECT, TRIGGER` re-grant to `authenticated` at line 275, which I verified matches the exact same idiom used on every other tenant table in this codebase, e.g. `company_kpis`/`research_runs` in earlier migrations — this is normal diff noise, not a widening); (2) the `anon` execute revoke on the new `public.expert_suggestions` function (lines 295-296, `private.is_active_expert` too); (3)/(4) the view-body/grant-widening the diff re-emits on `assigned_expert_summaries` and `expert_bookings` are explicitly *not* committed, called out in a trailing comment (lines 298-301) and in the sibling migration `20260913221714_spec_0022_company_currency.sql`'s header comment.
