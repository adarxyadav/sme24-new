# 0007. Company lookup and research pipeline

**Date**: 2026-09-06
**Status**: In Progress

## Summary

A client types their company name (and, if they have it, the website) on the dashboard, and a background job researches the company's public disclosures, extracts eight safety KPIs (key performance indicators such as the lost time injury rate) for the latest three reporting years, and stores each value with the web sources it came from. Parallel (a web research API that returns structured answers with citations) does the research inside a Trigger.dev task (a durable background job), and Claude checks every value against its cited excerpt before anything is saved. The dashboard follows the run live, shows the KPIs with their sources when it finishes, and gives the client a plain next step when nothing was found or the run failed. It is the core thread of the product; feature 9 adds the peer benchmark on top of the same rows.

## Requirements

**User stories**:
- As a client, I want to enter my company and see the research start at once so that I know the platform is working for me.
- As a client, I want to watch where the run is and how many sources it found so that a wait of a few minutes feels honest.
- As a client, I want every KPI value to show where it came from and how sure the system is so that I can trust it before I show it to my management.
- As a client, I want to correct my company details and run the research again when nothing was found so that a typo or a missing website does not leave me stuck.
- As an ops team member, I want a Slack alert with a link to the logs when a run fails so that I can fix the pipeline before the client writes in.
- As the engineer, I want the whole thread to run locally and in Playwright without spending research credits so that every change is provable.

**Acceptance criteria** (the contract, each criterion is IDed and independently checkable):
- **AC-1**: A data migration seeds eight active `kpi_definitions` rows, in this sort order: `ltifr` (per 1 000 000 hours worked, lower is better), `trifr` (per 1 000 000 hours, lower), `fatalities` (count, lower), `lost_days_per_incident` (days, lower), `accident_rate_per_1000_fte` (per 1 000 full time equivalents, lower), `absenteeism_rate` (percent, lower), `near_miss_rate` (per 100 employees, higher is better), `iso_45001_certified` (0 or 1, higher). Each row has `name` and `description` in `de` and `en`. The TypeScript catalogue in `src/features/research/catalogue.ts` lists the same eight keys with a plausible range, a parse rule and a one line extraction hint per KPI; a Vitest test asserts the two key lists match, and pgTAP asserts the eight rows are readable by a signed in client and not writable by one.
- **AC-2**: The same migration adds `research_runs.provider_run_id text null`, a partial unique index `research_runs_one_open_per_company_idx` on `(company_id) where status in ('queued', 'running')`, and the helper `private.research_run_allowed(organization_id uuid)` (true while the organization has fewer than 5 runs with `created_at` in the last 24 hours, not counting rows whose `error_code` is `trigger_failed`; `stale` rows count). The members insert policy on `research_runs` adds `and (select private.research_run_allowed(organization_id))`. It also adds a narrow members update policy on `research_runs` (`using`: own organization, `requested_by = auth.uid()`, `status = 'queued'`; `with check`: same organization and requester, `status in ('queued', 'failed')`) with `update` revoked from `authenticated` and re granted on the columns `status`, `error_code`, `error_message`, `trigger_run_id`, `finished_at` only (re add the column grant by hand in the migration, per the `AGENTS.md` diff gotcha), and amends the `company_kpis.sources` column comment to `retrievedAt`. The helper's count is not serialised, so two simultaneous inserts can overshoot the cap by one; the open run index bounds the damage and this is accepted. pgTAP proves: a second open run for the same company fails with a unique violation naming the index, the sixth run in 24 hours fails the policy with the code the action maps, a run created 25 hours ago and a `trigger_failed` row do not count, a member can move their own `queued` run to `failed` and set `trigger_run_id` but cannot touch `summary` or a `running` row, and an ops user is unaffected.
- **AC-3**: `/app` renders the lookup form when the organization has no company: the name prefilled from the organization's `name`, an optional website. The Zod schema in `src/features/research/schema.ts` trims the name to 2 to 200 characters and normalises the website with one rule: lowercase the host, drop path, query and fragment, force `https`, keep a `www.` the user typed (`example.ch` becomes `https://example.ch`, `www.example.ch` becomes `https://www.example.ch`, `https://Example.ch/reports?x=1` becomes `https://example.ch`). Submitting calls `requestResearch`, which in this order: selects the organization's non archived company and returns `company_exists` with its id when one exists; inserts the company (`name`, `website`, `country` `CH`, `created_by`); inserts the run as `queued` with `requested_by` (a failure here leaves the company in place, the rerun path takes over); triggers `research-company` with `{ runId }` under the idempotency key `research/<runId>` (global scope, 24 hour TTL); stores `trigger_run_id` through the members update policy of AC-2; and returns `{ ok: true, data: { companyId, runId } }`. The page then shows the dashboard with the run in `queued`, and within a minute the run is `running`. When the trigger call fails the action moves the run to `failed` with `error_code` `trigger_failed` and `finished_at` through the same policy, logs it, reports to Sentry when deployed, and still returns `ok: true` so the dashboard renders the failed state.
- **AC-4**: `research-company` is a `schemaTask` over `{ runId: uuid }` on the queue `research` (concurrency limit 5), `maxDuration` 900 seconds of compute, 3 attempts. It loads the run with the service client, then filters every read and write by that row's `id`, `organization_id` and `company_id`. A run that is already `succeeded`, `empty` or `failed` returns without doing anything. A `queued` run moves to `running` with `started_at` and `summary.step` `searching`; the provider run is created with the company's name, legal name, website and country plus the output schema derived from the catalogue, and `provider_run_id` is written before the first poll. A `running` run with a `provider_run_id` resumes polling that run instead of creating a new one; a `running` run without one (a crash between the status write and the create call) creates the provider run now. A resumed attempt writes `summary` and `provider_run_id` only, never `status`. Polling waits 15 seconds between checks with `wait.for` (skipped in fixture mode) and stops when the provider reports done or when 20 minutes of wall clock have passed since `started_at`; the budget spans attempts on purpose, and an attempt that starts past it fails at once with `provider_timeout`.
- **AC-5**: When the provider result is in, `summary.step` becomes `extracting` and one Claude call (AI SDK v7, `generateText` with `Output.object`, model `anthropic/claude-sonnet-5` through the AI Gateway, temperature 0) receives the catalogue (ranges, units, hints) and the provider output with its per field basis, and returns the object typed by `researchValidationSchema` in `src/lib/ai/schemas/research-validation.ts`: `values` (at most 24 items of `{ key, periodYear, value, sourceUnit, confidence, supported, reason?, sourceIndexes }`, where `value` is already converted to the catalogue unit, `sourceUnit` records what the source used, and `sourceIndexes` point into the provider's citations for that field) and `companyFacts`. A value is dropped when the excerpt does not support it (`unsupported`), when Claude could not parse or convert it (`unparseable`), when it falls outside the KPI's plausible range (`out_of_range`), when its year is outside 2000 to the current year (`bad_year`), or when a year is duplicated for the same KPI (`conflict`); on a conflict the value whose source host equals the company's website host wins, else the higher confidence, else the first in provider order, and the losing source is kept in the winner's `sources`. Every drop is recorded in `summary.dropped` with its reason. The prompt lives in `src/lib/ai/prompts/research-validation.ts`, exports `PROMPT_VERSION` (`research-validation@1`, bumped by hand when the text changes), and the version is stored in `summary.promptVersion`. When the call still fails after the SDK's retries, the run continues with the provider's values as parsed by the catalogue's parse rules, each confidence set to `min(basisPrior, 0.5)`, `summary.validation` `skipped`, and the failure reported to Sentry.
- **AC-6**: With `summary.step` `saving`, the task inserts one `company_kpis` row per kept value (`source` `research`, `research_run_id`, `kpi_key`, `period_year`, `value`, `confidence`, `created_by` null, `sources` as an array of `{ url, title, excerpt, retrievedAt }`) with `on conflict do nothing` on the run unique index, and fills `companies` columns `legal_name`, `uid`, `industry_code`, `employees_count` and `canton` with one statement of the form `update companies set legal_name = coalesce(legal_name, $1), … where id = $companyId` so a client edit in flight is never overwritten, each fact validated by `companyFactsSchema` (UID format `CHE-123.456.789`, canton one of the 26 codes, employees an integer at or above 0, NOGA code `dd` or `dd.dd`, legal name at most 200 characters). The run ends `succeeded` when a count of the run's `company_kpis` rows after the insert is at least 1 (a resumed attempt whose inserts were all conflicts still succeeds), else `empty`; the terminal write is guarded with `where id = $runId and status = 'running'` and a zero row result means the sweep or another attempt finished first, so the task logs and stops. The terminal update sets `finished_at` and the final summary: `version`, `step` `done`, `processor`, `sourcesFound`, `kpisExtracted`, `coverage` per KPI key (`found` or `not_found`), `years`, `sources` (deduplicated, at most 25), `text` (the provider's short summary, at most 1 000 characters), `companyFacts`, `dropped`, `validation`, `promptVersion` and `durations` (`searchMs`, `validationMs`, `totalMs`).
- **AC-7**: When the organization has a company, `/app` shows the company name and details, the latest run's status badge, a five step progress list (queued, searching public sources, extracting KPIs, saving results, done) with the live counters from `summary`, and, once the run is `succeeded` or `empty`, the KPI table: one row per catalogue KPI in sort order, one column per period year, the three newest years present in `company_kpi_current` for the company (a mixed set across runs and, later, client rows, accepted as such), each cell showing the value formatted by the catalogue's `format` (`decimal2`, `integer`, `percent1`, `yesNo`) with its unit, a confidence badge (high at or above 0.75, medium at or above 0.4, low below), a popover listing the sources with title, link and excerpt, a "not verified" mark when the row's run has `summary.validation` `skipped` (the query loads the runs for the distinct `research_run_id` values in a second query), and "not found" for an empty cell; a coverage line reads "n of 8 KPIs found". The run's source list sits below the table. The client component `run-progress.tsx` subscribes to the latest run's row (`postgres_changes`, filter `id=eq.<latestRun.id>`, re subscribing when the id changes after a rerun), calls `router.refresh()` every 5 seconds while the run is open as the fallback, and calls it once more when the status turns terminal so the table renders on the server. The page renders in German and English, its strings live in a `research` namespace, and it passes axe.
- **AC-8**: A run in `empty` shows an info alert that no public disclosures were found, a form with the editable details (name, legal name, website) and a rerun button; a run in `failed` shows a destructive alert with the message for its `error_code` and the same form. Both mention that manual entry arrives with a later feature (wording only). The form calls `rerunResearch(companyId, details)`, which updates the company's editable columns through the members update policy (a plain update, so the client's values always win over research; zero rows updated returns `not_found`), inserts the next run and triggers the task exactly as `requestResearch` does. The rerun button is disabled while a run is open or the daily quota is used up, and the page shows "n of 5 runs left today".
- **AC-9**: Both actions map a unique violation whose constraint is `research_runs_one_open_per_company_idx` (matched on the constraint name in the error details, never on the bare code, since other 23505 violations exist) to `run_in_progress`, and a row level security violation on the run insert (code `42501`; the action sets the organization and requester itself, so the quota is the only policy reason left) to `quota_exceeded`; the form shows the matching message inline. Any other database error returns `unexpected` and reaches Sentry. A Vitest test asserts the mapping against the exact error shapes recorded from the local stack.
- **AC-10**: Inside the task a network error, a 429 or a 5xx from the provider throws, so Trigger.dev retries with its default backoff and the retry resumes the stored provider run. A 4xx on creating the provider run (other than 429) fails the run at once with `provider_rejected`; the 20 minute budget fails it with `provider_timeout`; both use a non retryable error. The task's `onFailure` hook runs once, after the last attempt or an abort (a `maxDuration` kill lands here too and maps to `internal`): it sets `status` `failed`, `error_code` (`provider_rejected`, `provider_unavailable`, `provider_timeout` or `internal`), `error_message` (a short safe sentence without secrets) and `finished_at` with the guard `where id = $runId and status in ('queued', 'running')` (zero rows means the sweep got there first, so no alert), then fires the `research.run_failed` alert with `runId`, the organization's name, the reason, the idempotency key `research-failed/<runId>` (global scope) and `externalUrl` set to the Trigger.dev run page (`https://cloud.trigger.dev/projects/v3/<ctx.project.ref>/runs/<ctx.run.id>`). The `ops-alert` payload gains an optional `externalUrl` (https only), the builder signature becomes `buildSlackMessage(payload, { link, externalUrl, appUrl })`, and the button uses `link` when set, else `externalUrl`, else no button. Details go to Sentry with a `research_run_id` tag.
- **AC-11**: A scheduled task `sweep-research-runs` (every 15 minutes, declarative cron in UTC) marks runs `queued` for more than 30 minutes and runs `running` for more than 60 minutes as `failed` with `error_code` `stale` and `finished_at`, each update guarded by the row's current status, fires the alert for each with the idempotency key `research-stale/<runId>`, and logs the counts. A swept row frees the open run slot so the client can rerun; a task attempt that later reaches its terminal write finds zero rows under its guard and stops without a second alert.
- **AC-12**: `RESEARCH_PROVIDER` (`parallel` or `fixture`, on the task schema only) defaults to `fixture` when `PARALLEL_API_KEY` is empty, and a deployed task requires `PARALLEL_API_KEY` unless `RESEARCH_PROVIDER` is `fixture` explicitly (a `superRefine` on the task schema, since `requiredWhen` cannot express it). The fixture provider (`src/lib/research/fixture.ts`) reports done on the first poll, after about 2 seconds per step, with pinned constants: a full result of 8 KPIs for the years current minus 1 to current minus 3 with 5 sources for any name, an empty result when the name contains `empty`, and a provider failure when the name contains `fail` (case insensitive). A Playwright test drives the lookup through the fixture provider end to end when `TRIGGER_DEV_RUNNING` is set (the thread completes in under about 15 seconds), asserts the progress steps, the KPI table against the fixture constants, the empty state and the rerun, and runs axe on each state; without the worker it asserts the queued state only, and it skips on a deployment.
- **AC-13**: The provider input and the Claude prompt carry only the company name, legal name, website, country, the catalogue and the instructions; company names are in scope by design even when a sole trader's company name is a person's name. What never leaves is profile data (the requester's name, email address) and internal ids (organization, company, run, user). A Vitest test builds both payloads from a run row that also holds those and asserts none appear.
- **AC-14**: A member of another organization cannot read the company, the run or the KPI rows (the existing pgTAP files), `rerunResearch` for a company outside the caller's organization returns `not_found`, an expert or ops user opening `/app` gets the existing forbidden page, and the task never trusts an id from its payload beyond loading the run row (a Vitest test with a fake client asserts every write is keyed by the loaded row's ids).
- **AC-15**: Every step writes a structured log line through `log` with `runId`, `organizationId`, `companyId`, `providerRunId` and the elapsed milliseconds; unexpected errors reach Sentry with the `research_run_id` tag; the final summary's `durations` and `processor` make cost review possible without opening the provider console.
- **AC-16**: The env module validates `PARALLEL_API_KEY` and `RESEARCH_PROVIDER` for the task context and `.env.example` documents them; `docs/research.md` records the pipeline shape, the fixture mode, the error codes and the per environment checklist (Parallel key and billing, the AI Gateway key, the schedule registration on deploy, the Slack channel); the new progress list primitive and the confidence badge variant get a section on `/admin/design`.

## Decision

**Chosen option**: Option 1: Parallel does the research with a structured output schema derived from the KPI catalogue, Claude validates every value against its citation, and one Trigger.dev task runs the whole thing while the dashboard follows the run row over Realtime.

One durable task per run turns a company name into cited KPI rows; the database already holds the tables, the state machine and the access rules from spec 0002, so this feature adds the pipeline, the quota, the lookup form and the dashboard segment.

## Feature design

**Data model sketch** (the target; the tables exist from spec 0002, only the marked items are new):

| Entity | Kind | This feature | Keys and relations |
|---|---|---|---|
| `kpi_definitions` | G (global, exists) | **Seed** the eight rows of AC-1 by data migration (`insert … on conflict (key) do update` on the text columns, so a rerun of the migration is safe) | pk `key`; 1:N to `company_kpis` |
| `companies` | T (tenant, exists) | No columns. The action writes `name`, `website`, `country`, `created_by`; the task fills `legal_name`, `uid`, `industry_code`, `employees_count`, `canton` where null; the rerun form edits `name`, `legal_name`, `website` | pk `id`; fk `organization_id`; 1:N to `research_runs` and `company_kpis`; one company per organization in this feature (by the actions, not by the schema) |
| `research_runs` | T (exists) | **New column** `provider_run_id text null`; **new partial unique index** on `(company_id) where status in ('queued','running')`; **insert policy** gains the quota helper; **new members update policy** (own `queued` run to `failed`, column grants on `status`, `error_code`, `error_message`, `trigger_run_id`, `finished_at`); `summary` typed by `researchSummarySchema` (Zod, `src/features/research/summary.ts`) | pk `id`; fks `organization_id`, `company_id`, `requested_by`; 1:N to `company_kpis` |
| `company_kpis` | T (exists) | No columns. Rows with `source` `research` written by the task only; `sources` holds `[{ url, title, excerpt, retrievedAt }]` | pk `id`; fks `organization_id`, `company_id`, `research_run_id`, `kpi_key`; unique `(research_run_id, kpi_key, period_year)` |
| `private.research_run_allowed(uuid)` | helper (**new**) | `security definer`, `set search_path = ''`, counts the organization's runs in the last 24 hours excluding `error_code = 'trigger_failed'`, returns `count < 5`; execute revoked from `public` and `anon` | called by the insert policy only |

The UI lives in `src/features/research/ui/`: `lookup-form.tsx`, `run-progress.tsx` (client, Realtime), `kpi-table.tsx`, `sources-popover.tsx`, `rerun-form.tsx`; the progress list primitive is `src/components/ui/progress-list.tsx` and the confidence levels are new `Badge` usages, both on the gallery.

The `summary` shape (version 1): `{ version: 1, step, processor: 'core' | 'fixture', sourcesFound, kpisExtracted, coverage: Record<KpiKey, 'found' | 'not_found'>, years: number[], sources: { url, title, retrievedAt }[], text: string | null, companyFacts: { legalName?, uid?, industryCode?, employeesCount?, canton? }, dropped: { key, year, value, reason: 'unsupported' | 'out_of_range' | 'bad_year' | 'conflict' | 'unparseable' }[], validation: 'passed' | 'skipped', promptVersion: string, durations: { searchMs, validationMs, totalMs } }`. Counters and `step` are written as the task goes; the rest lands with the terminal status. The summary's `sources` list carries no excerpt on purpose (the run level list is for "where we looked"); the excerpt lives on each `company_kpis` row's `sources`.

**State transitions** (`research_runs.status`, the trigger from spec 0002 enforces them; `summary.step` is the finer progress inside `running`):

`queued` → `running` (task attempt 1 starts; `started_at`) → `succeeded` (at least one KPI row) | `empty` (none) | `failed` (`provider_rejected`, `provider_unavailable`, `provider_timeout`, `internal`, `stale`). `queued` → `failed` (`trigger_failed` from the action, or `stale` from the sweep). Inside `running`: `searching` → `extracting` → `saving` → `done`. A retry of the task never changes `status`; it continues from the stored `provider_run_id`. Terminal states are final; a new request is a new row.

**API surface** (the feature in `src/features/research/` with `schema.ts`, `actions.ts`, `queries.ts`, `catalogue.ts`, `summary.ts` and `ui/`; the provider layer in `src/lib/research/`; the AI module in `src/lib/ai/`; tasks in `src/trigger/`; actions return `{ ok: true, data } | { ok: false, error }`):

| Endpoint | Method | Key inputs | Key outputs | Auth | Key errors |
|---|---|---|---|---|---|
| `requestResearch` | server action | `name: string` (req, 2 to 200), `website: string` (opt, normalised per AC-3) | `companyId`, `runId` | client member with an organization claim | `validation`, `company_exists` (carries the existing `companyId`; the UI switches to the rerun form), `run_in_progress`, `quota_exceeded`, `unexpected` |
| `rerunResearch` | server action | `companyId: uuid` (req), `name` (req), `legalName` (opt, at most 200), `website` (opt) | `runId` | client member | `validation`, `not_found` (no row updated under RLS), `run_in_progress`, `quota_exceeded`, `unexpected` |
| `getCompanyDashboard` | query (server component) | the organization id from the session claims | `company`, `latestRun` (with the parsed summary), `kpis` (rows of `company_kpi_current` for the company joined to their run's `summary.validation`), `catalogue`, `quota: { used, limit: 5, remaining, openRunId }` | client member | throws on a database error (queries throw) |
| `research-company` | Trigger.dev `schemaTask` | `{ runId: uuid }` | the terminal status | service client, ids from the run row | throws on transient provider errors (retried); `AbortTaskRunError` for `provider_rejected` and `provider_timeout` |
| `sweep-research-runs` | Trigger.dev schedule `*/15 * * * *` | none | `{ queuedSwept, runningSwept }` | service client | throws on a database error (retried) |
| `ops-alert` (spec 0006, amended) | Trigger.dev `schemaTask` | `externalUrl?: https url` added to the payload | unchanged | unchanged | unchanged |
| Realtime subscription | browser | `postgres_changes` on `research_runs`, filter `id=eq.<runId>` | the updated row (RLS applies per subscriber) | signed in member | channel not healthy → the 5 second polling fallback |
| `ResearchProvider` (`src/lib/research/provider.ts`) | TypeScript interface | `createRun(input, schema)`, `getRun(providerRunId)`, `getResult(providerRunId)` | `{ providerRunId }`, `{ status: 'running' | 'done' | 'failed' }`, `{ fields, basis, text }` | task only | `ProviderRejectedError` (4xx), `ProviderUnavailableError` (429, 5xx, network) |

The provider output schema is flat, built from the catalogue at run time: `reporting_years` (the fiscal years found, newest first), then for each KPI three string fields `<key>_latest`, `<key>_previous`, `<key>_two_years_prior` (each "value and year, or 'not found'"), then `legal_name`, `uid`, `website`, `industry_noga`, `employees`, `canton`, `summary`. Flat string fields are what Parallel's basis cites per field; Claude parses value and year from each string.

| task | `period_year` per value | Claude's parse of the year inside the provider's field text; fallback the position in `reporting_years` |
| task | `confidence` | Claude's score with the provider's basis confidence as its prior (`low` 0.3, `medium` 0.6, `high` 0.9); capped at 0.5 when validation was skipped |
| task | `sources` per value | the provider basis citations of that field (`url`, `title`, `excerpt`), `retrievedAt` = the task's clock at result time |
| task | winner on a conflict | the source host equal to the company website host, else the higher confidence (AC-5) |
| task | plausible ranges | `catalogue.ts` per KPI |
| task | company facts written | Claude's normalised facts, written only where the column is null, validated by `companyFactsSchema` |
| failure handler | organization name for the alert | `organizations.name` through the service client |
| failure handler | `externalUrl` | `ctx.project.ref` and `ctx.run.id` from the task context |
| failure handler, sweep | alert idempotency keys | `research-failed/<runId>`, `research-stale/<runId>` (global scope) |
| task | `PROMPT_VERSION` | exported from `src/lib/ai/prompts/research-validation.ts` |
| sweep | the two age limits | constants 30 and 60 minutes in `src/trigger/sweep-research-runs.ts` |
| fixture | the canned result | `src/lib/research/fixture.ts`, names with `empty` or `fail` switch the outcome |

**Key invariants**:
- At most one open run (`queued` or `running`) per company, enforced by the partial unique index.
- At most 5 runs per organization per rolling 24 hours, enforced in the insert policy; the action's count is a courtesy, never the guard.
- `provider_run_id` is written before the first poll, so no retry creates a second paid provider run.
- Every `company_kpis` row with `source` `research` has a `research_run_id`, a `confidence` and at least one source; a value without a supporting excerpt is never stored.
- A stored value is inside its catalogue range and its `period_year` is between 2000 and the current year.
- The task filters every write by the ids of the run row it loaded; the payload's `runId` is used only to load that row.
- Research never overwrites a company column the client filled.
- The provider and Claude receive no person's name, no email address and no internal id.
- `research_runs.status` moves only along the spec 0002 transitions; a retry resumes, it never resets, and a resumed attempt never writes `status` until its own terminal write.
- Every terminal write (task, failure hook, sweep) is guarded by the row's current status, so two writers can never both finish a run or both alert on it.
- A client edit to `companies` always wins; the task only ever fills nulls with `coalesce`.

**Security model** (compliance scope: revised Swiss FADP with GDPR readiness, spec 0001):
- Client members read their organization's company, runs and KPI rows and insert runs (existing policies plus the quota); they update `companies` through the members update policy and their own `queued` run through the narrow update policy of AC-2 (five columns, `failed` as the only other status); they never write research rows.
- Experts read through `expert_assignments`, ops read and write everything (existing policies); no ops surface ships here, ops see failures in Slack and Trigger.dev.
- The task uses the service client (allowed in `src/trigger/`) with explicit ids; the sweep uses it for status only.
- The company name, legal name and website are public company data, not personal data, so this feature adds nothing to the consent path; the requester's identity stays in the database. Parallel and Anthropic (through the AI Gateway) are US processors; their data processing agreements are feature 14's list (spec 0001 Follow-up).
- Audit: `companies`, `research_runs` and `company_kpis` already carry the audit trigger, so every research write is logged with the service role as actor.
- Rate limiting: the database quota caps spend; the Vercel Firewall rule on the lookup action stays on the hosted checklist (spec 0001).

**Configuration required**:
- `PARALLEL_API_KEY` (task; required when deployed unless `RESEARCH_PROVIDER` is `fixture`): the Parallel API key. Prerequisite: a Parallel account with billing enabled per environment.
- `RESEARCH_PROVIDER` (task; optional, `z.enum(['parallel', 'fixture'])`): defaults to `fixture` when the key is empty; the "required when deployed unless fixture" rule is a `superRefine` on the task schema. `PARALLEL_API_KEY` stays optional on the server schema (no server code calls Parallel).
- `AI_GATEWAY_API_KEY` (task, exists): the validation pass reads it through the AI SDK's gateway provider.
- `OPS_ALERT_WEBHOOK_URL` (task, exists): the failure alert.
- Trigger.dev: the `research` queue and the `sweep-research-runs` schedule register on deploy (`deploy.yml` tasks job); staging needs one deploy after merge for the schedule to exist.

**Critical test scenarios** (each maps to an acceptance criterion in `## Requirements`):
- Happy path: a client submits name and website, the run moves through the five steps over Realtime, the fixture result stores rows for eight KPIs and three years, the table shows values, confidence and sources, and `sourcesFound` matches the summary, verifies **AC-3**, **AC-4**, **AC-6**, **AC-7**, **AC-12**
- Validation: a Vitest test feeds the validator a provider output with one unsupported value, one out of range value and two conflicting values for one year, and asserts the stored set, the winner, the lowered confidence and the four `dropped` entries, verifies **AC-5**
- Validation skipped: the AI call throws after retries, the run still succeeds with capped confidence and `validation` `skipped`, and the dashboard shows the mark, verifies **AC-5**, **AC-7**
- Failure case: the provider returns a 503 twice then done; the task resumed the same `provider_run_id` (one `createRun` call in the fake), verifies **AC-4**, **AC-10**
- Failure case: the fixture `fail` name marks the run `failed` with `provider_unavailable` after the retries, the alert payload carries the Trigger.dev URL, the dashboard shows the message and the rerun form, verifies **AC-8**, **AC-10**
- Quota: pgTAP inserts a second open run and a sixth daily run and expects the unique violation and the policy error; the action maps both to their codes, verifies **AC-2**, **AC-9**
- Empty: the fixture `empty` name ends the run `empty`, the alert and edit form render, the rerun inserts a new run and the counter reads "3 of 5 runs left today", verifies **AC-8**
- Stale: a queued row backdated 31 minutes and a running row backdated 61 minutes are swept to `failed` with `stale` and two alerts fire, verifies **AC-11**
- Race: the sweep fails a run while a fake attempt is mid save; the attempt's terminal update hits zero rows, logs and stops, and no second alert fires, verifies **AC-6**, **AC-10**, **AC-11**
- Resume: a second attempt on a run that already holds all 24 rows ends `succeeded`, not `empty`, verifies **AC-6**
- Update policy: pgTAP moves a member's own `queued` run to `failed` with `trigger_failed`, and expects an error when the same member touches `summary`, a `running` row or another member's run, verifies **AC-2**, **AC-3**
- Auth/permission: a member of organization B calls `rerunResearch` with organization A's company id and gets `not_found`; an expert opening `/app` sees the forbidden page, verifies **AC-14**
- Data leaving: the payload builders drop ids, emails and names from a run row that has them, verifies **AC-13**
- Catalogue: the migration keys equal the TypeScript keys, pgTAP counts eight active rows, verifies **AC-1**

## Consequences

**Positive**:
- The core thread of the product runs end to end with real jobs, real AI and real rows, and every KPI value is traceable to a cited source and a confidence.
- The pipeline is one task with one provider interface; a second provider, a different processor or a stronger validator is a change in `src/lib/research/` or `src/lib/ai/` only.
- The fixture mode keeps local development, Playwright and previews free of research spend and makes the flow deterministic to test.
- The quota and the open run rule live in the database, so a second tab, a replayed request or a direct insert cannot burn credits.
- Feature 9 (benchmark) and feature 10 (self assessment) read the same `company_kpi_current` rows and the same catalogue with no schema change.

**Negative / tradeoffs**:
- Two paid vendors per run (Parallel, then Claude), both in the US; a run costs real money and takes minutes, so the free funnel step has a hard cost per sign up that the quota only caps.
- The flat output schema (about 31 string fields) is what the provider cites best, but it is verbose, and a KPI added to the catalogue means three more fields and a prompt change.
- Confidence is a model judgment on a model's citations; it is honest about support, not a statistical guarantee. The dashboard must keep showing it as such.
- A validation outage degrades quality silently for the client (a small mark) rather than failing; ops only see it in Sentry.
- Polling every 15 seconds for up to 20 minutes is up to 80 status calls per run; cheap, but not free, and the wait is invisible in the Trigger.dev cost view except as run duration.
- The AI SDK major (v7) differs from the version spec 0001 named (v6); spec 0001 needs a one line note.

**Neutral**:
- The KPI catalogue is a data migration; changing a name or description is a migration, not an ops edit, until an ops surface exists.
- The task's `maxDuration` counts compute only; a run's wall clock is bounded by the 20 minute budget and the sweep, not by Trigger.dev.
- The `ops-alert` payload gains an optional `externalUrl`; spec 0006's registry and builder change by a few lines, and feature 12 switches the link back to an app path.
- `docs/research.md` becomes the runbook for the pipeline, beside `docs/auth.md` and `docs/email.md`.
