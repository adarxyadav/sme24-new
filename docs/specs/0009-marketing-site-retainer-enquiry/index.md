# 0009. Marketing site and retainer enquiry

**Date**: 2026-09-06
**Status**: In Progress

## Summary

The public site becomes four statically built pages in German and English (landing, pricing, about, contact) that all lead into the free benchmark, plus one enquiry form on the contact page that serves both the retainer package (sold by conversation, not by checkout) and general questions. Every page carries its own title, description, canonical link, language alternates, a generated social card and structured data (JSON-LD, the machine readable summary search engines read), and every page is in the sitemap. An enquiry is stored in a new `enquiries` table through a server action that guards against bots and floods, then alerts ops in Slack through the existing alert rail and sends the sender an acknowledgement email in their language; ops read and work the enquiries on a small `/admin/enquiries` page. No new service and no new secret: the pages are Next.js on the existing design system, the form is Postgres plus the tasks that already exist.

## Requirements

**User stories**:
- As a visitor from a search result or a shared link, I want to understand in one screen what SME24 does and start the free benchmark with my company name, so that I do not have to read a brochure first.
- As a visitor comparing options, I want to see the four packages with fixed prices in CHF and what each includes, so that I can put a number in front of my management before I sign up.
- As a company that wants an ongoing EHS partner, I want to ask for the retainer without creating an account, so that the first conversation is with a person.
- As a visitor with a question, I want a contact page with real contact details and a short form, so that I can reach the team either way.
- As a German or English speaking visitor, I want every page, every link and every social preview in my language, so that a shared link never lands me on the wrong language.
- As an ops team member, I want a Slack alert the moment an enquiry arrives and a page where I can read it and mark it as contacted or closed, so that no lead waits in a mailbox.
- As the owner, I want the site to rank and to load fast on a phone, so that the free benchmark works as the lead magnet the plan counts on.
- As the engineer, I want the copy, the prices and the contact facts in one place each, so that a price change is a one line edit and a test catches a placeholder.

- **AC-9**: `submitEnquiry` in `src/features/marketing/actions.ts` (a server action, always dynamic even when called from a prerendered page) parses the input with `enquirySchema` from `schema.ts`, and on success inserts one `enquiries` row through the service client (allowed in `src/features/*/actions.ts` by the Biome `noRestrictedImports` override) with `topic`, `company_name`, `contact_name`, `email`, `phone`, `headcount_band`, `message`, `locale` (a hidden field carrying the page language, validated `de` or `en`; it also says which page the form was on, so no separate path is stored), `ip_hash` (the SHA 256 hex of the first `x-forwarded-for` address, else `x-real-ip`, else null, from `headers()`), and, only when the caller's claims carry the `client` role, `organization_id` from the claims and `submitted_by` from `sub` (an ops or expert tester's submission stays anonymous). It then fires `sendOpsAlert` with kind `enquiry.received`, `organizationName` = the company name, `topic` = the human label ("Retainer" or "General question"), `link` = the bare path `/admin/enquiries/<id>` (the `ops-alert` task prefixes the app URL and the locale, as for every alert) and `idempotencyKey` = `enquiry/<id>/alert`, and `sendEmail` with template `enquiry_received` (added to `EMAIL_TEMPLATE_NAMES`, the closed enum that types the payload), recipient `{ email, locale }`, data `{ contactName, topic }`, `sourceEvent` = `enquiry.received` (the same string as the alert kind, so ops can correlate the delivery and the alert) and `idempotencyKey` = `enquiry/<id>/ack`. A failed alert or email trigger is logged and reported to Sentry and the action still answers `{ ok: true, data: { id } }`; the row is never lost. The action captures the server side PostHog event `enquiry_sent` with `distinctId` = the enquiry id and `{ topic, locale }` (a provisional name until feature 15 fixes the taxonomy).
- **AC-10**: Bot and flood guards, in this order before any database write: a filled honeypot field (`website`, visually hidden, `tabindex="-1"`, `autocomplete="off"`) or a submission less than 3 seconds after the form mounted (a hidden `startedAt` field the client component sets from `Date.now()` on mount, never the server component, because a prerendered page would bake one timestamp at build time for every visitor; a missing value is treated as a bot) answers `{ ok: true }` without storing anything and logs `enquiry rejected` with the reason; more than 5 rows with the same `ip_hash` in the last hour, or more than 3 rows with the same `email` in the last 24 hours (two count queries through the service client; the counts and the insert are not atomic, so the limit is best effort and two submissions in the same instant may both pass), answer `{ ok: false, error: "rate_limited" }` and the form shows `marketing.contact.form.errors.rateLimited` ("Please try again later or write to {email}", filled from `SITE.email`). A database error on the insert answers `{ ok: false, error: "unavailable" }` and reports to Sentry. Validation failures answer `{ ok: false, error: "validation", fields }` with the per field message keys.
- **AC-11**: One migration from `supabase/schemas/32_enquiries.sql` creates `enquiries` (kind I of spec 0002): `id uuid primary key default gen_random_uuid()`, `topic text not null check (topic in ('retainer', 'general'))`, `company_name text not null check (char_length(company_name) between 1 and 200)`, `contact_name text not null check (char_length(contact_name) between 1 and 200)`, `email text not null check (email = lower(email) and char_length(email) between 3 and 320)`, `phone text null check (char_length(phone) <= 40)`, `headcount_band text null check (headcount_band in ('1-49', '50-249', '250+'))`, `message text not null check (char_length(message) between 20 and 2000)`, `locale text not null check (locale in ('de', 'en'))`, `ip_hash text null check (char_length(ip_hash) = 64)`, `organization_id uuid null references public.organizations (id) on delete set null`, `submitted_by uuid null references public.profiles (id) on delete set null`, `status text not null default 'new' check (status in ('new', 'contacted', 'closed'))`, `handled_by uuid null references public.profiles (id) on delete set null`, `handled_at timestamptz null`, `ops_note text null check (char_length(ops_note) <= 2000)`, `created_at`, `updated_at` with the `set_updated_at` trigger; indexes `(created_at desc)`, `(status, created_at desc)`, partial `(ip_hash, created_at desc) where ip_hash is not null`, `(email, created_at desc)`, `(organization_id)`; the audit trigger attached `after insert or update of status, ops_note` only (personal data and ops decisions are audited; the purge's `ip_hash` null out and its deletes are not, they log their counts instead). A kind I table carries no tenant policy contract: no member policy, no `organization_id` isolation test. Policies, in the shape of `30_email_deliveries.sql` and `21_companies.sql`: `"enquiries: ops read" for select to authenticated using ((select private.is_ops()))` and `"enquiries: ops update" for update to authenticated using ((select private.is_ops())) with check ((select private.is_ops()))`; the policy says who, the column grant says what: `revoke insert, update, delete on public.enquiries from anon, authenticated` then `grant update (status, handled_by, handled_at, ops_note) on public.enquiries to authenticated` (re added by hand in the migration per the `AGENTS.md` diff gotcha); `service_role` keeps insert, select, update and delete (the action and the purge use it); `revoke truncate ... from anon, authenticated, service_role`. `supabase/tests/enquiries.test.sql` proves: anon and a client member cannot select, insert, update or delete; an assigned expert cannot select; ops select every row and update only the four granted columns (an update of `message` or `email` raises); the service role inserts and deletes; the check constraints hold; the audit trigger writes an `update` row on an ops status change and none on an `ip_hash` null out.

## Decision

**Chosen option**: Option 1: Everything in the app: static Next.js pages on the existing design system, one enquiry form backed by an `enquiries` table and the existing alert and email rails, a small ops page.

The public site is four prerendered pages in the `(marketing)` route group built from the campaign components of spec 0003, with copy in the two message catalogs, prices in one catalog file and contact facts in one site file. Discoverability is handled in the app too: per page metadata and alternates through the helpers of spec 0004, a generated social card per page and language, typed JSON-LD, and the existing sitemap fed by `MARKETING_ROUTES`. The single form on the contact page serves the retainer and general questions, writes to a kind I table through a server action with a honeypot, a timing check and two database counted rate limits, then fires the reserved `enquiry.received` alert and a new `enquiry_received` acknowledgement through spec 0006's rails. Ops work the enquiries on `/admin/enquiries`, built now in the shape of `/admin/emails` rather than waiting for feature 12. No headless CMS, no form service, no separate marketing host.

**Key invariants**:
- Every marketing page is static: no page or layout on the `(marketing)` path reads `searchParams`, `headers()` or `cookies()`. The server action may read `headers()` (a server action is always a dynamic request, even when the page that calls it is prerendered), and the query parameter reads happen on the client.
- Every public route is in `PATHNAMES` with its German slug and in `MARKETING_ROUTES`; `alternatesMetadata` is the only source of canonical and `hreflang` links, and the sitemap uses the same helper (spec 0004).
- The three fixed price packages always carry a positive price; the retainer never carries one. Prices are displayed excluding VAT; no page computes tax (feature 11 owns it).
- An enquiry row is written only by the service client from `submitEnquiry`; the app roles cannot insert, and ops can change only `status`, `handled_by`, `handled_at` and `ops_note`. The message, the contact fields and `ip_hash` are immutable after insert.
- `email` is stored lowercased and trimmed; `ip_hash` is a 64 character hex string or null and is never shown in any UI.
- The row is stored before the alert and the email are triggered, and the trigger keys `enquiry/<id>/alert` and `enquiry/<id>/ack` are global, so a retry of the action or a double click can never send twice for the same row, and a failed trigger never loses the row.
- A rejected bot submission writes nothing and still answers `ok`, so a bot cannot tell the honeypot from success.
- `handled_at` is set once, the first time the status leaves `new`, in the same statement as the status change (the row's current status decides, not a value read earlier), and never cleared.
- Every user facing string is a catalog key in both languages; the OG statement and the JSON-LD names are localized the same way.

**Security model** (compliance scope: revised Swiss FADP with GDPR readiness, spec 0001):
- The form collects contact data of a person (name, email, phone) and a company; the lawful basis is the person's own request, so no consent checkbox is asked; the form shows the privacy note with the link slot feature 14 fills. The data lives in Supabase Zurich; the acknowledgement email goes through Resend (or Mailpit locally) under spec 0006's rules, the alert to Slack carries the company name and the topic only, never the person's email or phone.
- Anonymous visitors read the static pages and call the one public action. The action runs with the service client because there is no session (the Biome `noRestrictedImports` override permits `@/lib/supabase/service` in `src/features/*/actions.ts` and `src/trigger/`); it is the only place outside `src/trigger/` that inserts into `enquiries`, and it never reads rows back except the two count queries. Only a `client` role links the row to an organization; ops and experts submitting the form (testing, a colleague's question) stay anonymous on the row.
- Ops (`app_metadata.role = 'ops'`) read every enquiry and update the four workflow columns through the server client under RLS; the proxy gates `/admin`, the action checks the role again from the claims. Clients and experts have no policy on the table; a client's own enquiry is not visible in `/app` (out of scope).
- `ip_hash` is pseudonymised personal data held for the flood guard only and nulled after 30 days; closed enquiries are deleted after 12 months (the retention rule goes into feature 14's record of processing). Deletion on request is an ops delete through the dashboard until feature 14 gives it a path.
- Every insert and every ops change of `status` or `ops_note` is audited by the trigger of spec 0002; an anonymous enquiry's audit row carries a null `organization_id` and the `service` actor, so it is visible in the global ops audit read, not in any per organization view. The purge's `ip_hash` null out and its deletes are not audited (the task logs its counts).
- The action rate limits by address and by email; the honeypot and the timing check cover the plain bots. No captcha (declined in spec 0005 as a follow up; still a follow up here) and no external bot service.
- No new secret. The font file and the campaign images are public assets.

**Configuration required**: none new. `NEXT_PUBLIC_APP_URL` (absolute URLs), `TRIGGER_SECRET_KEY` (alert and email triggers; without it both are logged as `trigger_unavailable` and the row is still stored), `EMAIL_ALLOWED_RECIPIENTS` on staging (the acknowledgement to an outside address is stored as `skipped`, expected) and `NEXT_PUBLIC_POSTHOG_KEY` (the server event is skipped without it) already exist. Prerequisites before `/check verify` passes the pricing and contact pages: the three prices and the contact facts from you (the Follow-up lists them); the engineer drafts the descriptions, the FAQ and the about story. The build runs with marked placeholders for your facts, and the AC-6 and AC-17 tests refuse them until replaced.

## Consequences

**Positive**:
- The whole public site ships as static HTML from the existing app, so it inherits the design system, the two languages, the typed routes and the alternates helper; there is nothing new to host, pay for or keep in sync.
- Every enquiry is a database row with an ops workflow and an audit trail from day one, and the alert and acknowledgement reuse the rails of spec 0006, so the lead path is as observable as the rest of the product.
- The lead magnet is one field on the landing page that carries the company name into sign up, which is the shortest path from a search result to a research run.
- Prices, contact facts and copy each live in one place with a test that refuses a placeholder, so a change is a one line edit and a wrong deploy is caught in CI.

**Negative / tradeoffs**:
- Copy changes need a deploy. A marketing person cannot edit a page without a pull request; a headless CMS is the follow up if that becomes a daily need.
- The flood guard is two counted queries in Postgres and a honeypot; a determined attacker with many addresses can still fill the table until ops notice. There is no captcha and no edge rate limiter, by choice.
- Generating the social card at build time means a Geist font file in the repo and one image route per page; a copy change to the statement rebuilds the image, which is right, but a broken font file breaks four routes at once (the build fails loudly, so it cannot ship silently).
- `/admin/enquiries` lands before the ops admin of feature 12, so feature 12 inherits a second admin page built in the `/admin/emails` shape and may want to fold both into its shell.

**Neutral**:
- The table is `enquiries`, not the `retainer_enquiries` spec 0002 reserved; the target map row moves at `/sync`.
- The legal footer group and the privacy link in the form are slots feature 14 fills; until then the footer shows two groups and the form's note links to nothing.
- The server side `enquiry_sent` event name is provisional; feature 15 may rename it when it fixes the taxonomy.
- Feature 11 promotes `PACKAGES` into the `packages` table; the pricing page keeps reading the catalog file, and a test keeps the two equal (the `kpi_definitions` pattern of spec 0007).
- `schema-dts` (types only) and the shadcn `Accordion` are the two additions to the dependency tree.
