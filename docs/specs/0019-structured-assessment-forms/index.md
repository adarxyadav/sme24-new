# 0019. Structured assessment forms

**Date**: 2026-09-12
**Status**: In Progress

## Summary

After a client has paid, an expert visits the company and rates it against a checklist. This spec turns Phillip's two checklists (ISO 45001 with its three annexes, and 18 technical standards with 327 requirements) into versioned data in the database, and builds one questionnaire engine that the expert fills in on the client's page under `/expert`: rate each item Compliant, Partially or Non compliant, add a note, everything saves as they go, and one Submit locks the assessment for good. Each questionnaire is its own assessment for the client (its own row, page, score and gap list), and a third one (Safety Culture) can be added later as content alone. Scoring is one pure function that the gap report (feature 18) reuses, and the client sees only that an assessment is running or submitted, never the working draft.

## Requirements

**User stories**:

- As the assigned expert, I want to open the client I am visiting and work through the ISO 45001 checklist or the technical standards on my laptop, so that my findings are structured data from the first minute and nothing lives in a spreadsheet.
- As that expert, I want every rating and note saved the moment I make it, so that a dropped connection in a plant or a closed lid never costs me an afternoon of work.
- As that expert, I want the annex sub checks to suggest a clause rating and the standards that do not apply to a site to drop out of the score, so that the score means what it says.
- As that expert, I want Submit to lock the assessment, so that the score the client and the report see is the one I signed off.
- As a client member, I want to see whether my booked assessment has started and when it was submitted, so that I know where my order stands, without seeing a half finished draft.
- As ops, I want the state of every assessment next to its order, so that I can chase a delivery or answer a client without asking the expert.
- As Phillip, I want the checklist content to live in files I can review and correct, in German and English, and to be able to change a standard later without touching past assessments.

**Acceptance criteria** (the contract, each criterion is IDed and independently checkable):

- **AC-1**: `pnpm questionnaires:build` reads the two raw HTML files (paths given as flags, defaulting to `docs/raw/iso45001_assessment.html` and `docs/raw/standards_assessment.html`), extracts the `<script type="application/json">` block of each, and writes `src/features/assessments/content/iso45001.json` and `compliance.json` in the content schema of `content-schema.ts`. The ISO file holds 7 sections and 60 items in document order (27 clauses, then the 33 annex sub items under their clause, 19 of them rateable); the compliance file holds 18 sections with 42 groups and 327 rateable items. Positions run 1 to N per file, and every item carries a display label restored from the raw numbering (the second `1.1`, `1.2` and `2.1` in a section become `1.10`, `1.20` and `2.10` in the ten affected standards). The text fixes in `content-fixes.ts` are applied (Hot Work 1.1 says hot work not line breaking; ISO 5.4 carries its own requirement; ISO 4.3 and the seven other clauses that say quality or customer satisfaction say OH&S; Electrical 3.3 has a requirement; no text contains `Lonza`; `7.5.` is `7.5`; `OHO&S` is `OH&S`), and a Vitest test over the committed files asserts every one of them. Every text is a `{de, en}` pair; a German text the script drafted carries `deReviewed: false`, and a rerun keeps a reviewed German text whose English source is unchanged.
- **AC-2**: `pnpm questionnaires:migration` renders `supabase/migrations/<timestamp>_questionnaire_seed.sql` from the committed JSON through a pure `renderQuestionnaireMigration`: one upsert per version and per item, never a delete, so a rerun changes no row count and a text correction within a version is a new generated migration. `questionnaire_versions` and `questionnaire_items` are kind G tables every signed in user reads and only ops may write through the API, with `truncate` revoked from the three app roles. A Vitest test keeps `QUESTIONNAIRE_KEYS` in the catalogue equal to the content files on disk and parses each file with the content schema; a pgTAP file asserts 60 and 327 items for `iso45001@1` and `compliance@1`, that every parent precedes its children, that every item's section and group exist in its version's outline, and the read and write rules.

- **AC-4**: `status` moves `draft -> submitted` exactly once: the `private.check_assessment_transition` trigger sets `submitted_at` on that edge and raises `invalid assessments transition` on every other change of `status`, and raises `assessment_incomplete` when any rateable top level item of a section that is not excluded has no rating. The `private.check_assessment_open` trigger on `assessment_answers` raises `assessment_locked` on any insert, update or delete once the parent is `submitted`, for every role including the service role, so a submitted answer set can never change. `classifyAssessmentError` in `errors.ts` maps each fragment to a typed action error, and a wrong assessment id or a foreign one is a `not_found`, never a 403.

- **AC-6**: `/expert/clients/[organizationId]/assessments/[assessmentId]` shows the assessment in the caller's language: a header with the questionnaire title, the company, the status, the progress (rated top level items over required ones) and the running score; a section navigator with per section progress that keeps the open section in the `section` search parameter; and for the open section every item with its label, title, requirement (collapsible), question, a three way rating control, a note field and a per item save indicator. ## Decision

**Chosen option**: Option 2: One questionnaire engine over versioned content rows, with the assessment as the unit the client sees and section exclusions stored as answer rows.

One engine (screens, rating, notes, autosave, scoring, submit and lock) serves every questionnaire; the content is data in two global tables, seeded from JSON files a hand run script builds from Phillip's HTML, keyed by position with a pinned version per assessment; each questionnaire is its own `assessments` row, page, score and gap list; the score is one pure function; and a standard the expert marks not applicable is a row in `assessment_answers` with no item, so it rides the same autosave, lock and policy path as every other answer.

## Feature design

### How the spec 0002 table contract applies

`questionnaire_versions` and `questionnaire_items` are kind G (global reference data): read by every signed in user, written by ops or a migration, not audited, `truncate` revoked, the `kpi_definitions` shape. `assessments` and `assessment_answers` are kind T under the tenant contract (an `organization_id` that cascades from the organization, the `(organization_id, created_at desc)` index, `set_updated_at`, the audit trigger, the ops full access policy, `anon` nothing) with the narrowings AC-3 lists, each written as a `DEVIATION` note at the top of the schema file the way `41_orders.sql` does: clients never write either table, clients never read answers, experts get insert and update policies here because this is the feature that names them. `expert_bookings` is a definer view (a view whose `where` clause is the access boundary, the `assigned_expert_summaries` shape) over `orders` exposing no money column; it is the one place an expert reads an order, a deliberate narrowing of the spec 0011 rule that experts do not read `orders`, and it exists because an expert has to know what is booked, when, and for which package.

### Data model sketch

**`questionnaire_versions`** (kind G, `supabase/schemas/60_questionnaire_versions.sql`). `key text primary key check (key ~ '^[a-z][a-z0-9_]*@[0-9]+$')` (`iso45001@1`, `compliance@1`), `questionnaire_key text not null check (questionnaire_key ~ '^[a-z][a-z0-9_]*$')`, `version integer not null check (version >= 1)`, `title jsonb not null` (`{de, en}`, the `kpi_definitions` check), `sections jsonb not null check (jsonb_typeof(sections) = 'array')` holding the outline in order (`[{key, label, title: {de, en}, groups: [{key, label, title: {de, en}}]}]`; `groups` is empty for ISO 45001), `item_count integer not null check (item_count >= 0)` (what the migration wrote, so a pgTAP count has a stated expectation), `source_note text null` (which raw file and export date the content came from), timestamps. `unique (questionnaire_key, version)` and `unique (questionnaire_key, key)` (redundant with the primary key on purpose: it lets `assessments` carry a composite foreign key that keeps `questionnaire_key` honest without a generated column). The newest version of a key is `order by version desc limit 1`; there is no status column, a seeded version is live, and a superseded one simply stops being newest while every assessment pinned to it keeps reading it.

**`questionnaire_items`** (kind G, `61_questionnaire_items.sql`). `id text primary key` (`<version key>/<position>`, `iso45001@1/12`), `version_key text not null references questionnaire_versions (key) on delete cascade`, `position integer not null check (position >= 1)`, `parent_id text null references questionnaire_items (id) on delete cascade` (an annex sub item points at its clause; a parent has a smaller position, checked by pgTAP), `section_key text not null`, `group_key text null`, `label text not null` (the display number: `4.1`, `1.10`, `A.3`), `rateable boolean not null`, `title jsonb not null`, `requirement jsonb null`, `question jsonb not null` (all `{de, en}`), `de_reviewed boolean not null default false`, timestamps. `unique (version_key, position)`; index `(version_key, section_key, position)`; index `(parent_id)`. A rateable item with `parent_id` null is a top level item, the unit of scoring; a rateable item with a parent is a sub item, rated for the suggestion only; a non rateable item is context text (ISO Annex A has ten such lines).

**`assessments`** (kind T, `62_assessments.sql`). `organization_id` (cascade), `company_id uuid not null references companies (id) on delete restrict`, `order_id uuid null references orders (id) on delete set null`, `questionnaire_key text not null`, `questionnaire_version_key text not null`, `foreign key (questionnaire_key, questionnaire_version_key) references questionnaire_versions (questionnaire_key, key)`, `expert_id uuid not null references profiles (id) on delete restrict`, `status text not null default 'draft' check (status in ('draft', 'submitted'))`, `site text null check (site is null or char_length(site) between 1 and 200)`, `conducted_on date null`, `submitted_at timestamptz null check ((status = 'submitted') = (submitted_at is not null))`, timestamps. Indexes: the contract one; `(expert_id, status)`; `(order_id) where order_id is not null`; unique partial `(company_id, questionnaire_key) where status = 'draft'` (one open draft per company and questionnaire, the `research_runs` shape). Column grants: `revoke update on public.assessments from authenticated; grant update (status, site, conducted_on) on public.assessments to authenticated;` (the diff misses this; fix by hand). No score column: the score is computed at read time from the pinned version and the answers, so it can never go stale and feature 18 computes the same number.

**`assessment_answers`** (kind T, `63_assessment_answers.sql`). `organization_id` (cascade), `assessment_id uuid not null references assessments (id) on delete cascade`, `item_id text null references questionnaire_items (id)`, `section_key text null`, `rating text null check (rating is null or rating in ('compliant', 'partial', 'non_compliant'))`, `note text null check (note is null or char_length(note) <= 4000)`, timestamps. Checks: `(item_id is null) <> (section_key is null)` (a row is an item answer or a section exclusion, never both, never neither), `item_id is not null or rating is null` (an exclusion carries no rating). Unique partial `(assessment_id, item_id) where item_id is not null`; unique partial `(assessment_id, section_key) where item_id is null`; index `(assessment_id)`. An item answer with `rating` null and a note is a note without a rating (allowed while drafting; the completeness check counts it as unrated). An exclusion row exists exactly while the standard is excluded.

**`expert_bookings`** (view, in `62_assessments.sql`, `security_invoker = false`). `id, organization_id, company_id, reference, package_key, package_name_snapshot, status, scheduled_at, delivered_at` from `orders` where `assigned_expert_id = (select auth.uid()) or (select private.is_ops())`, status in `scheduled`, `in_progress`, `delivered`. `revoke all from anon; grant select to authenticated`.

**Helpers** (schema `private`, `security definer`, `set search_path = ''`, execute revoked from `public`): `private.owns_assessment(assessment_id uuid) returns boolean` (a row exists with `expert_id = auth.uid()`); `private.can_edit_assessment(assessment_id uuid, org uuid) returns boolean` (that row is `draft`, belongs to `org`, and `private.is_assigned_expert(org)` holds); `private.check_assessment_transition()` and `private.check_assessment_open()` (below). Definer because the policies on `assessment_answers` must read `assessments` without recursing through its policies, the `is_org_owner` reasoning from spec 0002.

**Files.** `src/features/assessments/{catalogue,content-schema,content-fixes,translate,seed-migration,model,schema,errors,queries,actions}.ts`, `content/iso45001.json`, `content/compliance.json`, `ui/` (below), `scripts/build-questionnaires.mts`, `scripts/questionnaires-migration.mts`, `src/lib/ai/prompts/questionnaire-translation.ts` (`PROMPT_VERSION = "questionnaire-translation@1"`, a glossary of the official German ISO 45001 clause titles and the OH&S terms, Swiss spelling with ss). `catalogue.ts` holds `QUESTIONNAIRE_KEYS = ["iso45001", "compliance"]`, `QUESTIONNAIRES` (`key`, `allowsSectionExclusion`: true for `compliance` only), `RATING_CODES`, `RATING_VALUES` (`compliant: 1, partial: 0.5, non_compliant: 0`) and `PACKAGE_QUESTIONNAIRES` (`culture: []`, `sms: ["iso45001"]`, `compliance: ["compliance", "iso45001"]`, `retainer: []`; the ladder from `PACKAGES` in spec 0009 read as which checklists a package's visit runs).

### State transitions

```
assessments.status:   draft ──submit──▶ submitted        (once; no way back, no other state)
assessment_answers:   writable while parent draft; frozen for every role once submitted
questionnaire_versions: <key>@1 live ──new content file version──▶ <key>@2 newest; @1 stays for pinned assessments
```

`private.check_assessment_transition` (`before update of status`): `draft -> submitted` sets `new.submitted_at := coalesce(new.submitted_at, now())` after the completeness count passes (`raise exception 'assessment_incomplete: % items unrated'` otherwise); anything else `raise exception 'invalid assessments transition % -> % on %'`. Both use `errcode = 'check_violation'`. The count: rateable items of the pinned version with `parent_id` null whose `section_key` is not excluded and that have no answer row with a non null rating. `private.check_assessment_open` (`before insert or update or delete` on `assessment_answers`): `raise exception 'assessment_locked: %'` when the parent's status is `submitted`. Ops have no reopen; a correction after submission is a new assessment (Follow-up records the ops reopen question).

### API surface

All are server actions in `src/features/assessments/actions.ts` on the caller's own client (`createActionClient`), parsed by the Zod schemas in `schema.ts`, answering `{ ok: true, data }` or `{ ok: false, error }` and never throwing for an expected failure. No service client is needed anywhere in this feature: every write is allowed by a policy or a column grant, and the database holds the guards.

Autosave in `section-items.tsx`: one in flight save per item, coalescing (a change made while a save is in flight is sent after it lands, latest value wins), a rating change saves at once, a note change saves 800 ms after the last keystroke or on blur, three retries with backoff on a network or unexpected failure, then `failed` with a manual retry; `beforeunload` is registered while any item is pending or failed. A `locked` result switches the whole page to read only through a `router.refresh()` and a toast. Two devices of the same expert overwrite each other per row, last write wins; there is no per row version check (Follow-up).

| `saveAnswer` | `rating` value | the rating code; its number is `RATING_VALUES` in the catalogue, read only by `model.ts` |
| `setSectionExclusion` | whether allowed | `QUESTIONNAIRES[key].allowsSectionExclusion` from the assessment's `questionnaire_key` |
| `submitAssessment` | `submitted_at` | the trigger, `now()` on the server |
| `submitAssessment` | the unrated count per section on `incomplete` | `computeProgress` in `model.ts` over the page's data, recomputed on the server after the trigger refuses |
| page | the running score, the progress, the suggestion | `computeScore`, `computeProgress`, `suggestedRating` in `model.ts` over the pinned version's items and the answers |
| page | content language | `LOCALE_CODE[locale]` picking `de` or `en` from each jsonb column |
| page | the machine translated note | `de_reviewed = false` and the locale is `de` |
| client card, ops table | the state per order | `listAssessmentStates` joined on `order_id`; `not started` when no row |
| alert | the company name, expert name, score | `companies.name`, `profiles.full_name` read in the action after the write, `computeScore` |
| analytics | `organizationId`, `assessmentId`, `questionnaireKey`, `orderId`, `locale` | the row just written and `LOCALE_CODE[locale]` |

### Key invariants

1. An assessment is pinned to one version for life: `questionnaire_version_key` is never updated (outside the column grant) and a version's items are never deleted, so a submitted score can always be recomputed to the same number.
2. `draft -> submitted` happens once, only when complete, and nothing writes an answer of a submitted assessment, whichever role asks (the two triggers).
3. One open draft per company and questionnaire (the partial unique index).
4. A score counts only rateable top level items of sections that are not excluded; sub items and context lines never count; an excluded section is neither counted nor required.
5. Every answer row belongs to the assessment's organization and is either an item answer or a section exclusion (the checks and `can_edit_assessment`).
6. Content identity is position, never Phillip's number: a label is display text; `item_id` and `position` are the keys.
7. Every content text has both languages (the jsonb checks); a machine drafted German text is flagged until a person clears it.
8. No client member reads an answer (no policy) and no client member writes either table (no policy); a client route never queries `assessment_answers`.

### Security model

Compliance scope: the answers are the client organization's data (the revised FADP applies as it does to every kind T table); notes are free text an expert types and may name people, so the UI asks the expert not to record individual workers' names and the record of processing lists the tables with `account` retention. Audit: both T tables carry `private.audit_row`, so every rating and note change is in the audit log with its actor.

| Who | `questionnaire_*` | `assessments` | `assessment_answers` | `expert_bookings` |
|---|---|---|---|---|
| client member | read | read own organization's rows; no write | nothing | nothing |
| expert | read | read assigned organizations' rows and own rows; insert own draft for an assigned organization; update `status`, `site`, `conducted_on` of own draft | read own; insert, update, delete on own draft while assigned | own bookings |
| ops | read; insert and update through the ops policies | all through the ops policy, updates beyond the three columns need the service client | all | all |
| anon | nothing | nothing | nothing | nothing |
| service role (tasks) | all | all, but the lock trigger still refuses a submitted answer set | all under the trigger | all |

The proxy gates the expert area; RLS is the boundary. A foreign or unknown `assessmentId` is a `notFound()` from the page and `not_found` from an action. Rate limiting: none beyond auth, the writes are per authenticated expert on their own rows. Secrets: `AI_GATEWAY_API_KEY` is read by the build script from `.env.local` and never committed; the raw HTML lives in the gitignored `docs/raw/`.

### Configuration required

No new environment variable. The build script reuses `AI_GATEWAY_API_KEY`. New scripts in `package.json`: `questionnaires:build` (`node scripts/build-questionnaires.mts [--iso <path>] [--standards <path>] [--no-translate]`, the last flag refusing to write unless every German is reused) and `questionnaires:migration` (`node scripts/questionnaires-migration.mts`). `PATHNAMES` gains the assessment route. `ANALYTICS_EVENTS` and `ALERT_KINDS` gain their entries.

## Consequences

**Positive**:
- Content is data with a pinned version per assessment, so Phillip can change a standard and no past score moves; a third questionnaire is two files and a migration.
- The database holds every guard (one draft, complete before submit, locked after, expert only writes, clients never read answers), so the actions stay thin and a bug in the UI cannot leak or corrupt a draft.
- One pure scoring function means the expert's running score, the locked score, the ops alert and feature 18's report can never disagree.
- Exclusions ride the answer path, so they autosave, lock and audit like a rating with no extra policy or grant.

**Negative / tradeoffs**:
- Autosave writes often, and every write is an audit row: an expert session on the 327 item questionnaire can add a few thousand `audit_log` rows. Acceptable at the pilot's volume; the debounce keeps it bounded; a retention rule for the audit log stays feature 14's open item.
- The German is machine drafted and shipped flagged. Until a person reviews it, German speaking experts read a note on every item; the flag is honest but visible.
- No offline mode. An expert in a plant without signal keeps unsaved values in the page and sees `failed` with a retry, but closing the tab loses them; the warning before unload is the only net. A real offline queue is a Follow-up, not this spec.
- No reopen after submit. A mistake found after Submit means a new assessment, which is deliberate (the locked score is the one the client was told) but will annoy an expert once.
- Two levels of item (clause and annex sub item) and two kinds of answer row (item and exclusion) make `model.ts` and the queries carry a few branches that a flatter model would not.

**Neutral**:
- Two more hand run scripts join the benchmark pair, with the same "commit the generated file" rule.
- `expert_bookings` is the first read of `orders` by an expert; spec 0011's rule narrows to "no money column" and the view is where that is enforced.
- The `assessments` update grant is three columns; ops writes beyond them (a reassignment, a reopen if ever decided) go through the service client the ops admin pattern already uses.
- The audit log records the actor of every rating; the record of processing gains four rows.
