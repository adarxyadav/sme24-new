## Structured assessments

Questionnaire content is data, never code: `pnpm questionnaires:build` writes `src/features/assessments/content/*.json` from the raw exports in the gitignored `docs/raw/` and `pnpm questionnaires:migration` renders the seed as upserts only, so a rerun changes no row count. Item identity is `position`, never the printed label, and every content text is a `{de, en}` pair whose machine drafted German carries `deReviewed: false` until a person clears it. `questionnaire_versions` and `questionnaire_items` are kind G reference data; `assessments` and `assessment_answers` are kind T with the narrowings written as `DEVIATION` notes at the top of each schema file: a client member never writes either table and never reads an answer at all, an expert writes answers only on their own `draft`, and `authenticated` may update only `status`, `site` and `conducted_on`. An assessment pins its `questionnaire_version_key` for life, so a content correction never moves a past score. Every guard is a trigger, never app code: `private.check_assessment_transition` allows `draft -> submitted` once and refuses an incomplete submit, `private.check_assessment_open` refuses any answer write once the parent is submitted for every role including the service role, and `classifyAssessmentError` in `errors.ts` maps each raised fragment to a typed action error. A section exclusion is an `assessment_answers` row with a null `item_id`, so it autosaves, locks and audits on the same path as a rating; a questionnaire whose catalogue entry sets `allowsSectionExclusion: false` (ISO 45001) answers `not_allowed`. `computeScore` in `model.ts` is the one scoring function in the codebase (feature 18 imports it) and counts only rateable top level items of sections that are not excluded, so an annex sub item rating is stored but never counted. Client and ops status surfaces read the narrow `AssessmentState` from `listAssessmentStates`, which cannot carry a score or a note. Strings live in the `assessments` namespace in both catalogs. `expert_bookings` is a definer view over `orders` exposing no money column, the one place an expert reads an order. The per environment checklist and the German review loop live in `docs/assessments.md`.
