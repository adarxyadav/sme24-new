# src/features/benchmark

Moved out of the root `AGENTS.md` so it loads only when this area is touched. The root keeps a one line pointer here.

## Peer benchmark (spec 0008)

The `benchmark-company` task runs after a research run ends `succeeded` (key `benchmark/run/<runId>`), after `updateCompanyFacts` in `src/features/benchmark/actions.ts` (key `benchmark/edit/<companyId>/<updated_at>`) and on `pnpm benchmarks:recompute`; it hands stored rows to the pure `computeBenchmark` in `src/features/benchmark/model.ts` and inserts one immutable `benchmark_snapshots` row (written only by the service role), which the dashboard reads through the version keyed `SNAPSHOT_SCHEMAS` in `snapshot.ts`; no model call anywhere. A formula change bumps `MODEL_VERSION` in `src/features/benchmark/catalogue.ts` and adds a schema to the map, never rewrites old rows. Peer values and the seven assumptions live in `supabase/seed-data/*.csv` and reach the database only through `pnpm benchmarks:migration`; every first seed row is `provisional`, and the launch gate in the runbook requires zero provisional rows in production (spec 0016 split that flag from `is_assumption`, so the gate is two queries).

## Derived injury counts (spec 0012)

The expected yearly lost time and recordable injury counts are a display only `derived` block of the benchmark snapshot, never a KPI: `kpi_definitions` gains no row, `company_kpis` gains no source, and the counts never appear in `inputs.kpis`, `results` or `gaps`. `exposureCount(shape, rate, fte, hoursPerFte)` in `src/features/benchmark/model.ts` is the one place a rate becomes a count, dispatching on the rate's shape (`per_1000_fte` or `per_million_hours`) rather than on `costAt`'s incident union; `costAt` delegates only its `incidents` line, and the two may name different input rates on purpose (`rationale.md`). The whole block is `null` without a positive `inputs.fte` or without the `hours_per_fte` assumption row, and no derived value ever carries a confidence. `SNAPSHOT_SCHEMAS` in `snapshot.ts` is keyed by literal versions (`"benchmark-model@1"`, `"benchmark-model@2"`, `"benchmark-model@3"`, `"benchmark-model@4"`), so a `MODEL_VERSION` bump adds a key and never renames the only one; the `benchmark-company` task looks its write schema up by version rather than naming a schema, or zod strips the new block before the insert. A deploy owes `pnpm benchmarks:recompute`, watched: a stored row keeps the version it was written under until it is recomputed, and a recompute moves every block, not just the derived one. The script keys each trigger on `benchmark/recompute/<companyId>/<UTC day>` with a 24 hour TTL, so a second run on the same UTC day hands back the earlier runs and writes no new row; a post deploy recompute needs a UTC day no earlier recompute used. On the page the counts are plain rows of `CalculationFacts` at the top of the "How this is calculated" disclosure in `ui/benchmark-segment.tsx`, beside the computed on date, the KPIs compared count and the confidence driver; the opportunity card carries only the lost time count as a clause under the working estimate and no badge (owner decision of 2026-09-13, spec 0012 Follow-up), so anything that explains the arithmetic goes in the disclosure, not the card.

## Peer honesty (spec 0016)

Two flags, never both true: `provisional` means a value has not yet been read from its named source, `is_assumption` means no published source exists for it, so the launch gate is two queries and only the three `indirect_multiplier*` rows may answer the second. A peer row's shape is derived from its values in `seed-migration.ts` (`p25 == median == p75` is a `point` row), never a CSV column and never hand typed; a point row gets `above_average` or `below_average` from `positionOf` (the `iso_45001_certified` branch routes through the same rule), renders text only with no `QuartileBand` and no replacement graphic, and the words quarter, quartile and median never appear on it in either language, which `tests/features/benchmark/catalogue.test.ts` enforces over both catalogs. The CHF headline is a range on the card and in the `benchmark_ready` email alike, both rounded outward by `roundChfRange` in `model.ts` so the displayed band always contains the computed one and the two surfaces can never disagree for one snapshot. A curator's caveats reach the client rather than dying in the database: `source_key` and `basis` on a peer row, `note` and `isAssumption` on an assumption. Every KPI declares a `peerStatus` and a `peerNote` in `src/features/research/catalogue.ts`, so a sourceless KPI says so instead of looking pending. `docs/benchmark.md` records the confirmed dead ends; do not re investigate them.
