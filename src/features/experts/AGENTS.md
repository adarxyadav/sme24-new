## Expert accounts and profiles

Ops invite from `/admin/experts/new` through `inviteExpert`, which calls the shared `inviteStaffUser` in `src/lib/auth/invite.ts` — the same module `pnpm user:invite` runs, so the page and the script create the same rows in the same order and the role is a literal in the action, never a form field. The `expert_profiles` row is created at invite time with the email copied onto it, so the ops list is one query. `set_expert_status` is the only write path for the status and `set_expert_photo` the only one for `photo_path`, so both columns sit outside the profile action's column grant; assignment eligibility is the `check_expert_assignable` trigger in the database, never the app, so a deactivation racing an assign can never land on an inactive expert. Photos live in the private `expert-photos` bucket at `<expert_id>/photo.<ext>` and every read is a ten minute signed URL through `photoUrl` on the caller's user client, never a public URL and never the service client. Every list field is a code from `EXPERT_CATALOGUE` in `src/features/experts/catalogue.ts` with both labels, kept equal to the check constraints by a Vitest test, so adding a standard is a migration; strings live in the `experts` namespace in both catalogs. `deactivateExpert` is idempotent on purpose (status, then the open assignments, then the ban), so a failure part way through is fixed by pressing the button again. The three emails and the `expert.onboarded` alert ride the rail in `docs/email.md`; the invite itself stays an auth email on the Supabase path in `docs/auth.md`. The per environment checklist (the bucket, a real invite, the Slack alert, the three emails, `/admin/emails`) lives in `docs/experts.md`.
