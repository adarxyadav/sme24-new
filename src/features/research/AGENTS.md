# src/features/research

Moved out of the root `AGENTS.md` so it loads only when this area is touched. The root keeps a one line pointer here.

## Company research

`requestResearch` in `src/features/research/actions.ts` inserts the company and a `queued` run and triggers the `research-company` task under the idempotency key `research/<runId>`; the database holds the guards (one open run per company, five runs per organization per rolling 24 hours), never the app. Providers implement the interface in `src/lib/research/provider.ts` (Parallel and the fixture are interchangeable; a second provider is a file in that folder); `RESEARCH_PROVIDER` is `fixture` whenever `PARALLEL_API_KEY` is empty and a deployed task without the key refuses to start. Every model call goes through `structuredOutput` in `src/lib/ai/gateway.ts` (AI SDK v7 through the AI Gateway, prompts versioned in `src/lib/ai/prompts/`); nothing else imports `ai`. A new KPI is a `kpi_definitions` seed row plus a catalogue entry in `src/features/research/catalogue.ts` (a Vitest test keeps them equal); a new error code is a `research_runs.error_code` value plus `research.errors.<code>` keys in both catalogs. The per environment checklist (Parallel key, gateway key, schedule, Slack, spike, firewall) lives in the runbook.

## One organization holds several companies

`requestResearch` no longer refuses a second company: the `companies` table was always built for several per organization (a group and its subsidiaries) and every child table is company keyed, so this was app layer only. What is left of the old guard is `settleConcurrentCompany`, which now archives a duplicate of the **same name** rather than any second company, because a double click must not spend two runs on one question while a genuinely different company must pass. The daily quota still counts per organization, so several companies share the five runs; that is the brake on provider cost and there is no cap on how many companies a client may add (owner decision of 14 Sep 2026).

`/app/companies` lists them and `/app/companies/[companyId]` renders one; `/app` keeps opening the organization's earliest company so existing links still land. All three share `ui/company-dashboard.tsx` (`CompanyDashboardView`), which holds the render order the page used to own — read it, not the routes, before changing what the client sees. `getCompanyDashboard` takes an optional `companyId` and falls back to the earliest company without one, which is what the expert's read only mirror (`getAssignedClient`) still wants.

A run is two tasks, not one (spec 0022): `research-company` writes the client's own figures and then triggers `research-peers` (`src/trigger/research-peers.ts`, the `research` queue, its own 20 minute budget, key `peers/<runId>`), which finds the named companies the benchmark ranks the client against. Peers never decide a run's status, raise no alert and never write `research_runs.status` or `error_code`; whatever happens, the peer task's last step and its `onFailure` hook both trigger `benchmark-company` under `benchmark/peers/<the peer task's own run id>` (one value across the attempts of one search, a new one per genuine re-search, so re-running a peer search writes a fresh snapshot instead of being deduplicated), and `research-company` triggers it itself under `benchmark/run/<runId>` when the peer trigger fails, so a benchmark is always queued. The country is a required input on all three forms and sets `companies.currency` through `currencyOf`; nothing in the pipeline names Switzerland. The peer half is documented in `docs/benchmark.md`, not here.
